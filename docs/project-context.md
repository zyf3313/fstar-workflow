## 用户明确表达的目标

用户长期使用 Trellis，认为其完整工作流效果很好。希望参考它的思路，整体开发一个属于自己的新工作流，不满足于仅为每个 Trellis 项目提供一套规范模板。

新系统应以个人使用为核心：公共通用内容保存在个人仓库，并能安装到全局；在不同项目间切换时，Agent 能直接识别和使用这些能力。处理小事不需要在当前目录初始化项目工作流；需要正式持续开发时，再自动准备项目级工作流。

当前用 Trellis 管理新项目的开发，不代表未来产品必须依赖 Trellis。

## 最需要保留的 Trellis 使用体验

1. 整套工作流会规范地按既定模式推进，适时触发相应能力。
2. 调研使用探索能力；需求探索和沟通自然进入需求澄清。
3. 澄清后根据真实场景判断是否需要技术设计，不强制所有任务生成相同文档。
4. 执行阶段派子 Agent 工作，主 Agent 继续与用户沟通。
5. 用户中途补充或变更需求时，主 Agent 能把变化传递给执行者并推进修改。
6. 实施完成后主动派发检查，发现问题后形成修复与复查闭环。
7. 有值得保留的经验时主动进入规范沉淀，减少后续返工并帮助理解项目。
8. 最后完成归档。
9. 文件和区域职责清晰，让 Agent 只读必要上下文，避免无目的地广泛读取。
10. 保留类似“继续当前任务”的能力，能恢复工作并推进下一步。

轻量不意味着去掉完整闭环，而是按需要启动阶段、加载资料和创建产物。现有扩展库里的能力属于扩展点，不应让核心变重。

> **2026-10-28 随「最小内核 + 扩展包」定案的精确化**：本段「按需启动阶段、加载资料、创建产物」的表述在 §12 中被拆成两部分——**底座**是永远可用的最小闭环（澄清 → 执行 → 基础检查 ↔ 修复 → 用户确认，不落盘），**扩展包**按需协商加载（默认整包、可裁剪、拒绝后不重复问）。不再有「轻量/正式」任务类型。

用户认可按 task 管理工作，但不喜欢一个大需求拆成多个分散任务、主要通过 JSON 关联才能理解整体关系。

## 助手提出的设计方向（待正式评审）

### 总体结构

全局个人入口 → 按需建立项目上下文 → 主任务及内部子任务 → 主 Agent 协调、子 Agent 实施和检查 → 项目知识与个人记忆分别沉淀 → 收尾提醒和整体归档。

### 状态与恢复

> 本节已被下方「状态机结论（已确认）」取代，保留作讨论历史。

建议区分实施完成、待检查、待收尾和已归档，避免仅凭一句“完成”推断任务结束。

## 状态机结论（2026-10-25 已确认）

以下为用户明确拍板的结论，不再属于“助手建议”待评审项。

### 元决策

- 父子任务**共用同一套状态机**。叶子节点自己实施自己检查；容器节点聚合子节点状态，自身只负责规划和整体验收。
- **用户验收独立成闸门状态**，不合并进 `done`。Agent 最高只能推到 `awaiting_acceptance`。
- 状态转移的**权威在系统**，不在 Agent 自觉。系统校验转移合法性。
- **所有任务都要过验收闸门**，包括无子任务的轻量任务。轻量任务少的是产物和阶段跳转，不是验收。（**2026-10-28 随 §12 更新**：无「轻量任务」类型；最小闭环不落盘、不建凭证链，但**底线③「完成只能由用户确认」始终保留**——省的是产物与持久化，不是确认）
- 状态写入**强制走命令**（如 `task state set`），命令内部校验；同时提供巡检命令发现被手改坏的 `task.json`。
- 同一任务**单写者租约**。其他会话只读，或显式接管（原租约作废并记录）。

### 状态的三个维度

| 维度 | 含义 | 性质 |
|---|---|---|
| 阶段 phase | 走到哪一步 | 标量、互斥、可推进 |
| 证据 evidence | 支撑当前阶段的产物 | 可失效 |
| 在途 ownership | 谁在做（会话租约） | 可丢失、可过期 |

`blocked` **不是阶段**，而是阶段上的属性 `{ reason, since }`，解除后回到原阶段。`dropped` 是终态阶段。

### 阶段与合法转移

```
drafting → planned → implementing → checking → awaiting_acceptance → done → archived
   ↑            ↑            │        ↑ │
   │            │            │        │ │
   └────────────┴────────────┼────────┘ │
        （回规划：证据 stale + 租约释放） │
                            └── fixing ──┘
```

| 转移 | 触发者 | 必须存在的证据 |
|---|---|---|
| `drafting → planned` | Agent | prd；复杂任务另加 design/implement |
| `planned → implementing` | Agent（需用户确认记录） | 用户启动确认 |
| `implementing → checking` | Agent | 实施交付物（变更清单 + 自检结果） |
| `checking → fixing` | Agent | 检查报告 `verdict=fail` |
| `fixing → checking` | Agent | 修复交付物 |
| `checking → awaiting_acceptance` | Agent（系统校验） | 实际检查通过、用例获用户 approved 且指纹新鲜，证据覆盖当前需求/设计/用例及交付版本 |
| `planned/implementing/checking/fixing → drafting` | Agent | 回规划原因（需求/设计根本性变更，或 debug 判定根因在需求侧）；全部证据标记 stale；租约释放 |
| `awaiting_acceptance → done` | **用户** | 用户验收记录 |
| `done → archived` | 用户确认后系统执行 | 归档判据全满足 |
| `done → implementing` | **用户**（重开） | 重开原因 |
| `* → dropped` | **用户** | 放弃原因 |

系统必须硬拒：Agent 写 `done` 或 `archived`、`drafting → implementing`、`checking → done`、stale 证据下进 `awaiting_acceptance`、容器在子节点未全 `done`/`dropped` 时进 `awaiting_acceptance`。

### 证据失效

证据携带 `validates` 版本指纹。需求、设计、用例或交付版本变更导致指纹变化时，证据标记 `stale`，有效状态自动落回 `checking`。历史不被抹掉，可区分“哪一版检查过、哪一版没过”。

### 聚合与归档

- 容器进度由子节点**推导**，不落盘重复字段；容器自身的 `drafting`/`planned` 是显式状态。
- 归档判据：`phase=done` ∧ 子节点 ∈ {`done`,`dropped`} ∧ 无 stale 证据 ∧ 无未决问题。
- 主任务整体归档，不单独归档子任务。
- 提醒触发：进入项目、开始其他任务、用户主动询问。提醒说明缺失项，支持暂缓与去重。**提醒不是自动归档。**

### 在途与孤儿

`implementing` / `checking` 挂租约（owner 会话 + 心跳）。心跳超时标记 `orphaned`。「继续」据此区分：活跃租约（报进度、不重复派发）/ 租约失效（提示继续、重派或放弃）/ 无租约（正常派发）。

任务内存租约，会话内存“我上次在哪个任务”，**不存在全局当前任务指针**。

## 宿主平台能力验证（2026-10-25，Claude Code）

> **结论已降级**：本节的探针结果只证明「Claude Code 上的平台原生子 Agent 具备这些能力」。用户指出这不代表其他平台，因此**不把本节推导当作工作流的设计前提**。多平台能力改由复用 Trellis 的 channel runtime 解决，见下一节「复用 Trellis 已有抽象」。

用探针 Agent 实测，不是查文档。以下结论**仅对 Claude Code 原生子 Agent** 成立。

| 能力 | 结果 | 证据 |
|---|---|---|
| 并行派发多个子 Agent | ✅ | 两个 Agent 同时在跑 |
| 运行中向子 Agent 发消息 | ✅ | 第 2~3 轮之间送达并改变行为，剩余 8 轮被中止 |
| 取消在途 Agent | ✅ | 第 8 轮停止，之后 30 秒心跳无增长 |
| 恢复被取消的 Agent | ✅ | 恢复后完整记得原任务，中断被感知为显式停止信号而非上下文丢失 |
| 子 Agent 运行中主动上行 | ✅ | 第 3 轮主动发出进度消息，当时仍在运行 |

### 由验证结果推导出的约束

1. **消息送达发生在下一个工具轮次**，不是即时。因此执行 Agent 必须**小步工作**（每轮一个可检查的动作），否则中途变更会延迟到长任务结束才被看到。协议应要求执行者按检查点分段，而不是一条长命令跑到底。
2. **`orphaned` 不必丢弃工作重来**。恢复保留完整上下文，所以租约接管的首选动作是「唤醒原执行者并告知变化」，重派是后备。
3. **双向通信成立**，变更传导不是单向广播：执行者能主动报告阻塞、发现和偏差，主 Agent 不必轮询。
4. **派发本身会失败**（实测遇到一次分类器超时）。派发必须带重试与明确失败状态，不能假设一次调用必成功。
5. 恢复由主 Agent 发起，子 Agent 不能自我唤醒。所以租约心跳只能证明「还活着」，不能证明「会自动继续」。
6. **子 Agent 默认不一定加载 SendMessage**，实测需先用 ToolSearch 拉取 schema 才能上行。因此派发模板必须显式包含「加载消息工具」这一步，不能假设子 Agent 天然能回报。

### 尚未验证

- 会话级中断后（关闭终端、进程退出）能否恢复整个主会话与子 Agent 树。
- 子 Agent 嵌套派发（孙 Agent）是否成立。
- 并发派发的数量上限与 token 成本。

## 复用 Trellis 已有抽象（2026-10-25 决策）

用户判断：Trellis 已在多个 Agent 平台验证过，凡它做得好的能力应直接仿照/复用，不必从单平台探针重新推导通用契约。经源码与 CLI 核实，Trellis 0.6.17 已提供两层现成抽象，正好覆盖此前从零设计的部分。

### 1. `CLIAdapter`（`trellis/dist/`，平台适配层）

抽象 18 个平台的差异：claude、opencode、cursor、iflow、codex、kilo、kiro、gemini、antigravity、devin、qoder、codebuddy、copilot、droid、pi、trae、omp、grok、kimi。负责构造各平台的运行命令与输出解析。

### 2. `trellis channel`（多 Agent 协作运行时）

平台中立的对等进程模型，**不依赖 `.claude/`、`.codex/` 等任何平台目录**。这是此前「文件信箱」设计的成熟实现：

| 此前从零设计的机制 | Trellis 现成实现 |
|---|---|
| 文件信箱 / 事件传递 | `~/.trellis/channels/<project>/<channel>/events.jsonl`，append-only、序列锁、可重放 |
| 派发实施/检查 Agent | `channel spawn --agent implement\|check`（对等进程，非平台子 Agent） |
| 变更传导 | `channel interrupt`：打断 worker 当前轮并投递替换指令 |
| 租约 / 心跳 / 孤儿 | `worker_guard`：`idle_timeout` 默认 5m、`max_live_workers` 默认 6 |
| 等待与同步 | `channel wait --kind done --from <worker>`，支持 `--all` 多 worker 汇聚 |
| 全局 vs 项目 | `--scope project` / `--scope global` |
| Agent 角色定义 | `.trellis/agents/*.md`，平台无关角色卡 |

**关键结论**：channel runtime 用「对等进程 + 事件日志」而非「平台原生子 Agent 实时消息」，因此本文件前节探针结论中的延迟约束、恢复方式等，**对 channel worker 不适用**。平台中立性由 runtime 保证，不由每个平台各自保证。

### 3. 工作流模板机制

`trellis workflow --template <id>`，内置 `native` / `tdd` / `channel-driven-subagent-dispatch` / `marketplace`。工作流文档用条件块（如 `[Claude Code, Cursor, ...]` / `[codex-inline, Kilo, ...]`）在同一份文件里表达平台差异，而非维护多份文档。

### 对自研工作流的含义

1. **不再自造多平台 Agent 协作层**。直接以 `trellis channel` 为运行底座，或至少以其为设计蓝本。
2. **能力契约不必自己定义**，Trellis 的 runtime 已经隐式给出了。
3. 自研的增量价值应集中在**它没有的部分**：主任务内含子任务的目录组织、状态机（验收闸门、证据失效）、归档提醒、全局个人记忆。这些才是用户明确要而 Trellis 没有的。

- ~~`trellis channel` 是否可独立于 Trellis 的 task/spec 层单独使用~~ → **已确认可独立**：channel 与 task 状态完全解耦，唯一联系是用于显示过滤的 `--task` 字符串，worker 从不读写 `task.json`。

## 架构路线决策（2026-10-25，**已被 2026-10-27 的完全自研决定取代**）

> ⚠️ **本节保留作讨论历史。** 当时的「fork Python task 层 + 复用 `trellis channel`」方案已被 2026-10-27 的决定取代：协作层的 channel 复用 → 自研协议；task 层的 fork → 完全自研。见下方「2026-10-27 决策」。
>
> 本节仍有价值的部分：**许可边界的分析方法**（AGPL 义务取决于复制/修改范围、是否构成衍生作品、分发方式）——这套判断方法在评估任何第三方代码时都适用。

用户当时拍板：**fork 项目内 Python task 层 + 复用 `trellis channel` 作为协作层。**

### 理由

1. Python task 层（`.trellis/scripts/`）是 Trellis **官方指定的项目内定制点**，与模板逐字节相同，可自由 fork；`trellis update` 只会标记为已修改。nvm 下的 JS CLI/core 才是不可动部分。
2. `task.py archive` 与验收闸门语义冲突（强写 `completed`，唯一闸门是分支校验，可从 `planning` 直接归档），**无法包装，必须替换**。
3. channel runtime 平台中立且与 task 解耦，直接复用即可获得 18 平台协作能力，不必自研。

### 许可边界（必须明确）

fork Python task 层等于复制 AGPL-3.0 代码。

- **修正此前过度概括的说明**：AGPL-3.0 允许商业使用；不能把“给别人用”一概等同于“整个仓库所有内容都必须采用 AGPL”。义务取决于复制/修改范围、是否构成受覆盖的组合或衍生作品、分发方式，以及修改版的远程网络交互等条件。
- 复制或修改上游代码需要按适用条款保留版权、许可及修改说明；分发和修改版网络服务可能产生提供对应源码的义务。
- 仅调用独立 CLI 与复制其源码是不同的复用形式，不能未经评估就判定许可覆盖范围。公开发布前需根据实际集成方式核对。
- 目录名称和通用组织惯例的相似，不等于复制源码或模板；开源合规与是否准确表述原创贡献也需分别处理。

### 版本控制

本项目自身 `.trellis/` **纳入版本控制**（用户决定）。平台生成文件（`.claude/` 等）的处理另行决定。

### 盘点结论摘要

Trellis 0.6.17 的 task 层只有 `planning`/`in_progress`/`completed` 三状态，且 `completed` 在正常流程中是死状态（源码注释自承留待 "future status-transition redesign"）。四项自研增量在 Trellis 中**全部为零**：

| 能力 | Trellis 现状 |
|---|---|
| 用户验收闸门 | 无。`archive` 从不检查 prd、测试或 `check.jsonl` |
| 证据与失效 | 无。全包零 `evidence` 字段，无新鲜度计算 |
| 归档提醒台账 | 无。`completed` breadcrumb 是文档承认的死代码 |
| 全局跨项目记忆 | 无。`trellis mem` 是只读索引器，搜的是各家 AI 自己的 transcript |

### 三条决定性架构事实

1. **任务完成由目录位置定义，不由记录的结果定义。** `children_progress` 判子任务完成的方式是「不在 `.trellis/tasks/` 里」。任何验收/证据模型必须在 `shutil.move` **之前**写入 `task.json`；移动后 active 指针已被删除。
2. **channel 与 task 完全解耦，耦合是绿地决策。** 要建立「worker 完成 → 记录证据」「验收通过 → 停止 worker」，全是新代码，接入点是事件日志的 `done`/`error`/`killed`。
3. **Trellis 任务布局是扁平同级目录 + JSON 关联**，与用户要求的「目录体现归属」冲突，需改为嵌套 `subtasks/`。

### 执行期间的变更

主 Agent 判断补充与范围变更，更新任务依据并通知受影响执行者。优先避免多个执行者同时修改同一处代码；必要时暂停或重新派发。需求变化可能使已有检查证据失效。

这些是期望行为；不同宿主平台的实时消息、后台执行、取消和恢复能力仍需验证。

### 知识沉淀

建议分别保存任务事实、项目规范和个人跨项目偏好。主动识别候选经验，不强行每次都新增规范。明确的跨项目用户偏好可进入个人记忆；局部实现经验不应自动升级为全局规则。记忆应支持修正、替换、删除及来源追踪。

### 分阶段开发

建议先支持一个主要使用的 Agent 平台，验证完整闭环后再扩展。子 Agent 实施与检查是用户重视的核心体验，不能简单推迟为可选后续功能。扩展市场、广泛平台适配和 Storybook 门户可以后续评估。
