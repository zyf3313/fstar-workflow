# 文档整改样稿：从这里开始评阅

日期：2026-11-21。性质：设计样稿，尚未作为模板或运行规则启用。

## 建议先看什么

1. 先读 [开发计划样稿](development/plan.md)，对照此前“信息挤在一段里”的问题，判断现在是否能看清执行顺序、产出与验证。
2. 再读 [非开发计划样稿](research/plan.md)，检查同样的原则是否适用于普通事项，而没有套用 PRD、代码文件等开发概念。
3. 需要了解目标来源和决策记录时，看 [开发澄清样稿](development/clarify.md) 与 [非开发澄清样稿](research/clarify.md)。

开发例子来自已归档任务，但只在本目录中制作样稿，未重写历史。非开发例子完全虚构，设备、预算、偏好和权限均不是当前用户的真实信息。

## 两类文件各负责什么

| 文件 | 重点回答 | 不重复承担 |
|---|---|---|
| clarify.md | 为什么做、做到什么程度、哪些决定已确认、还有什么未知 | 详细执行步骤或整段聊天 |
| plan.md | 先做什么、如何做、产出什么、怎样检查、遇阻如何调整 | 完整重写目标和方案讨论 |

真正的阶段状态只保存在任务的 task.json。样稿目录没有创建子任务或模拟状态文件，不代表已进入实施。

## 这次刻意展示的变化

- 用独立成果和依赖划分步骤，不按固定文件数量或工具调用次数拆任务。
- 关键步骤写清输入、行动、产出、完成判据、依赖及调整条件。
- 将事实、假设、用户确认与推荐区分开，不把“被告知”当作“已确认”。
- 可以边做边确认的细节不阻塞全部工作；目标变化才需要重新约定。
- AI 根据实际能力选工具；偏好不能代替事实核实，也不自动扩大权限。
- 计划和验证记录分开，禁止把预计结果写成已经通过。
- doc/ 只在需要独立交付或详细说明时创建，目录名称不要求所有事项都生成产品需求和技术设计。

## 细度如何缩放

两组样稿都按中等复杂度展开，目的是让用户能评阅质量。它们不是要求每个事项写同样长度。

- 简单事项：一句目标、必要的完成条件、结果记录即可，不强制 clarify.md 或 plan.md。（此为待评阅的样稿建议，尚未成为生效规则）
- 多步骤事项：记录关键决定与执行步骤；常规低不确定性步骤可以简写。
- 复杂事项：关键决策和容易误解的边界展开，详细研究或方案按需要拆入 doc/ 或 research/，通过链接引用。

## 需要评阅的重点

- 计划是否更接近你想看的内容，哪些地方仍太概括或过细？
- 读完是否能判断目标、下一步和完成依据，是否仍有无价值的重复？
- 非开发事项的表达是否自然，是否还有明显的开发流程套用？

这轮先收敛样稿质量。文档确认不等于已批准具体 schema、工具接口或生产实现。

## 下一步整改顺序

1. 按反馈修订样稿。
2. 提炼文件职责、生成条件、内容质量要求和示例，形成模板与 Skills 调整设计。
3. 分析状态、证据、条目标记、指纹与旧任务的兼容影响。
4. 实施后用多场景生成、跨会话接手和需求变更验证，而不是只检查标题存在。

当前检查依据见 [文档检查记录](../research/document-audit.md)，已确认方向见 [本任务澄清记录](../clarify.md)。
