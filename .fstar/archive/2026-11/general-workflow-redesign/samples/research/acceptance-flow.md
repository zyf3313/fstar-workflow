# 调研样例：从验收到交付的完整流程（设计演示）

> 待评阅的设计样稿。延续 [调研计划样稿](plan.md) 的虚构场景；所有约定、价格、偏好均为示例，不代表当前用户。本文件演示新验收程序的样子，未执行任何调研，也不是现行规则。

## 一、验收标准在实施前就建立

需求澄清结束时（示例约定见 [澄清样稿](clarify.md)），主 Agent 把目标转成可判断的标准，写入任务根目录的 `criteria.md`。此时计划还没开始执行。

`criteria.md` 每条标准回答五个问题：

| 条目 | 依据（为什么有这条） | 场景与期望 | 检查方法 | 证据要求 / 判定边界 |
|---|---|---|---|---|
| A1 离线能力 | 用户要求“断网能用” | 无网络时可打开并编辑已有笔记 | 官方文档核实 + 试用环境断网实测 | 官方说明或实测记录；仅能查看不能编辑不算满足 |
| A2 数据可导出 | 用户要求“不想搬不出来” | 笔记正文、附件、内部链接可导出为通用格式 | 官方导出说明 + 实际导出验证 | 每个候选附导出格式清单与来源日期；只导出正文不算完整 |
| A3 费用核实 | 预算约定 ≤500 元/年 | 满足 A1/A2 所需档位的实际价格 | 价格页截图或读取记录，注币种与日期 | 无法核实标"未验证”，不推测 |
| A4 候选不超过三个 | 约定的交付形式 | 对照表 + 首选/备选推荐 | 清点交付物 | 超出个数须说明理由 |
| A5 交付物形式 | 用户在澄清收尾选择的偏好 | 报告放用户指定目录，用户习惯的排版 | 交付时对照 | 与用户选择不一致即未满足 |

A5 体现了 `doc/` 移除后的新机制：交付物存放在用户偏好位置，`deliverables.json` 只登记指针和对应验收条目。

## 二、执行中的检查与标准的关系

计划执行时，每个步骤的完成判据直接引用标准编号（“本步产出需覆盖 A1/A2 的证据”），而不是重写一遍要求。执行者自查通过不等于验收——标准是独立的裁判依据。

实施中如果发现某条标准本身有问题（例如 A2 的"通用格式"定义不清），回到澄清记录补一条决定，同时更新标准并注明修订原因。标准跟需求走，不允许静默改动。

## 三、实施完成后的验收程序

```text
实施完成
   │
   ▼
① 执行者自查（引用标准编号，报告差距）
   │
   ▼
② 独立检查（全新 Agent 实例，限定范围）
   · 输入：criteria.md + 用户关键原话 + 成果本身
   · 核对三条线：理解是否正确 / 成果是否符合约定 / 交付是否可用
   · 不采信执行者的"已完成"声明，只认证据
   · 任务大且条目独立时可拆多个实例并行
     （按标准条目切，不按文件切；各自全新实例）
   · 发现问题 → 退回执行者修复 → 只复查受影响条目
   │
   ▼
③ 最终检查（全新 Agent 实例，只读，不并行）
   · 汇总各并行检查的结果，对整体负责
   · 逐条对照 criteria.md 与有效证据
   · 核对用户关键原话，查遗漏/误解/擅自增加
   · 不修改任何文件；产出检查记录（checks/check-001.md）
   · 汇报三段式：达成项+证据 / 未验证项+原因 / 需用户判断项
   │
   ▼
④ 用户验收
   · 用户判断"是不是我想要的"（A5 的主观部分在这里）
   · 接受 → completed；发现问题 → 打回，证据按影响范围作废
```

**修复后的复查是局部的**：改了 A1 相关内容，只重查 A1 和受影响条目，A3/A4 的有效证据继续可用。全量作废只发生在目标或范围变化时——这解决“改一处文案重走全程”的问题。

**证据仍然内容寻址**：报告文件变了，指向它的证据自动过期，防止“检查通过后又改了报告”。

## 四、检查记录长什么样

`check-001.md`（示例片段）：

```markdown
# 检查记录 001 · 最终检查（只读）
- 检查者：独立实例（未参与实施与修复）
- 对照版本：criteria.md @ abc123 / 报告 @ def456
- 环境：…（实际执行环境说明）

| 标准 | 方法 | 结果 | 证据 |
|---|---|---|---|
| A1 | 官方文档 + 断网实测记录复核 | 通过 | 来源日期在有效期内，编辑能力有实测 |
| A2 | 导出说明 + 实际导出验证 | 通过 | 格式清单与实测一致 |
| A3 | 价格页读取记录 | 未验证 | 候选C价格页需登录，未获授权 |
| A5 | 对照用户交付偏好 | 通过 | 位置与格式符合澄清时的选择 |

未验证项与原因：A3 候选C——等待用户决定是否提供账号授权
需用户判断：候选B与首选的取舍（界面偏好，标准无法代替）
```

用户拿到的是这样的信息，而不是一句“调研完成，报告已生成”。

## 五、新旧程序对比

| 环节 | 现行程序 | 新程序 |
|---|---|---|
| 验收依据 | R/D/P 条目散在需求文档 | criteria.md 集中、实施前定、引用用户原话 |
| 检查者输入 | 需求文档 + 代码 | 标准 + 用户关键原话 + 成果 |
| 检查者权限 | 可自修代码 | 中间检查修复退回执行者；最终检查只读 |
| 检查范围 | 文档一致性 + 命令结果 | 理解正确性 + 符合约定 + 交付可用三条线 |
| 打回代价 | 证据全作废重走 | 局部作废，有效证据复用 |
| 检查方法 | 围绕测试命令 | 按成果类型：实测/来源核实/对照/用户判断分层 |
| 非开发场景 | 无对应方法 | 同一套协议，方法按场景适配 |
