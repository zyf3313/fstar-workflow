# 开发样稿：新工作树沿用项目规范

> 文档整改样稿，待评阅。以已归档任务 worktree-shared-data-root 为来源，示范如何表达当时的目标和决定；不是重新启动该任务，也不覆盖历史记录。以下“已确认”均指来源任务记录，不代表本轮新增确认。实现细节须在实际执行时重新核实。

## 1. 要解决的问题

用户在使用不提交 `.fstar/` 的项目时，新建 Git 工作树后，AI 无法获得主工作树中积累的规范与任务上下文。用户需要在不同工作树继续使用同一项目的资料，避免每次复制或重新解释。

来源中的用户原话（节选，省略开头“对了在开发过程中还遇到了个场景就是”）：
> 创建一个工作树不会把之前那个项目中的沉淀的fstar文件夹下的规范都带过去因为是git那个忽略提交的那个文件就忽略了 所以新开个工作树就没有带过去有没有办法去解决这个场景呢

## 2. 完成后应当是什么样

| 条件 | 期望结果 | 验收依据 |
|---|---|---|
| 主工作树使用 project-local 模式并已初始化 | 新工作树内可直接访问同一项目的规范、身份与任务 | 隔离仓库中，从两个工作树查询并比较数据根与内容 |
| 主工作树未初始化，当前工作树也没有可用项目数据 | 告知需要初始化，不自动创建或复制资料 | 操作返回可理解的提示，相关目录没有新增数据 |
| 共享已经生效 | 诊断信息指出资料来自哪个主工作树 | 诊断结果与实际解析来源一致 |
| 普通项目或已有其他存储配置 | 保持该模式原有语义，不误绑定另一个项目 | 模式回归与冲突情形验证 |

最后一项是执行前需要验证的兼容目标，不意味着它已由本样稿证明。

## 3. 已确认的范围与边界

历史澄清记录明确记载的四项决定：
- 规范、索引、身份与任务全部共享，不只共享规范。
- 识别到适用的工作树后自动共享，诊断中说明来源，不增加用户必填开关。
- 主工作树也没有数据时引导初始化，不隐式写入。
- user-directory 模式保持既有行为，并做回归确认。

本次目标不包含复制资料、放宽已有路径绑定规则，或自动提交、合并和发布。

## 4. 已知事实、假设与未知

**历史核实事实：**问题主要涉及被 Git 忽略的 project-local 数据；原有解析可以识别 `.git` 文件，但当时没有通过 commondir 共享主工作树数据根。以上是历史基线，不能当作今天代码仍然如此。

**已选方向：**通过 Git 工作树关系定位共享来源，让同一项目继续使用一份资料。

**执行前必须核实：**现有显式路径、用户目录模式和工作树自身数据的优先级；异常布局下如何保持既有行为。这些技术未知可通过调查和隔离测试解决。如果发现需要改变已约定的存储语义，才回到用户决定。

## 5. 方案取舍

| 方案 | 判断与理由 |
|---|---|
| 共享主工作树数据根 | 符合已确认目标，避免规范和任务出现多个版本 |
| 每次创建工作树时复制 `.fstar/` | 不采用：后续会产生资料漂移，且需要维护同步机制 |
| 放宽原有指针绑定规则 | 不作为默认路径：会改变已有路径身份约束，需要单独论证 |

## 6. 决定如何变化

目前样稿只呈现历史记录中的最终决定，没有编造新的变更历史。后续若调整范围，应记下变更内容、来源和受影响的计划步骤；不能静默覆盖原决定。

## 7. 接下来怎样推进

按 [执行计划样稿](plan.md) 先核实解析优先级和验证入口，再形成可检验的实现，最后交付用户能观察到的共享行为和证据。

本样稿刻意按较小信息量演示，因此只写澄清记录和计划；这演示的是新版"按需生成"的写法，不构成对历史任务的回顾评价——历史任务的 doc/prd.md 与 doc/design.md 保留为来源，其 commondir 与 pointer 语义细节仍被计划参考。确实需要独立评阅的复杂解析设计，仍可补充 doc/ 下的设计文档。
