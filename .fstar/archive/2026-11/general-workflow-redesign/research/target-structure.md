# 优化后完整任务结构（设计稿）

日期：2026-11-21。性质：待评阅的设计稿，尚未固化为模板或生效规则。配合 [澄清记录](../clarify.md) 的 C-01..C-20 阅读。

## 设计原则

- **核心独立（C-14）：**工作流只依赖磁盘状态和检查协议运转；外部工具是可替换的扩展。
- **按需生成（C-09）：**文件服务事项，事项不伺候文件。简单事项允许极简。
- **状态单一权威（C-06/C-17）：**阶段和运行状态只在 task.json；文档是理解和交接的载体，不是第二状态机。
- **约束与推荐分离（C-15）：**少量硬约束保护事实与授权；其余做法由 AI 按事项选择。

## 一个事项在磁盘上的完整样貌

```text
.fstar/tasks/<task-name>/
├── task.json                      ★ 必备 · 唯一状态权威
│     phase（四阶段）/ status（运行态：推进中/等待输入/
│     等待外部/暂停）/ work_items[]（进展与取消）
│     / next_step（下一步及依据）/ 决定与依据的事件日志
│
├── clarify.md                     ◐ 按需 · 有持续澄清或重要决策时
│     目标与原话依据 / 已核实事实与来源 / 已确认结论
│     / 假设与未知 / 取舍 / 被替代决定
│
├── criteria.md                    ★ 正式交付必备（C-13）
│     每条：依据 / 场景与期望 / 检查方法 / 证据要求 / 判定边界
│     （实施前确定；从 acceptance/ 子目录上移到根目录）
│
├── checks/                        ◐ 有检查记录时
│     check-001.md（最终检查）…
│     过程性检查（执行中/修复复查）记录并入同目录按序号递增；
│     单份简短过程记录可直接写 check.md 放根目录
│
├── plan.md                        ◐ 按需 · 多步骤或有交接需要时
│     整体思路 / 步骤（输入·行动·产出·完成判据·遇阻处理）
│     / 验证与交付 / 调整条件
│
├── deliverables                   ◐ 有对外交付物时 · 交付指针与证据
│     登记在 task.json 的 deliverables 字段内（设计稿 doc/design.md §4：
│     减少独立文件；路径、版本、格式、对应验收条目）。
│     交付物实际位置由用户偏好决定（澄清完成时引导询问一次，
│     之后按习惯沿用，C-09）
│
├── research/                      ◐ 仅当调研文件多时
│     单份结论直接写 research.md 放根目录；
│     来源多、过程长才展开成目录
│
└── subagents/                     ◐ 仅当派发记录多时
      后台派发的交接档案（每次派发一份交接单：版本、依据、
      范围、完成条件、返回结果、是否已被新决定取代）；
      单次派发直接写 subagents.md 放根目录，
      并行多 Agent 才展开成目录
```

★ 必备 　◐ 按需生成

**扁平化规则：**固定且单数的文件（clarify、criteria、plan）一律在根目录；`checks/`、`research/`、`subagents/` 只在内容确实多时才作为目录存在，起步形态是根目录的单个 `check.md` / `research.md` / `subagents.md`。交付指针登记在 task.json 内，不再单独成文件。打开任务目录即可看到全部核心文件，不需要逐层翻。

**检查的并行拆分（大任务加速）：**当任务量大、标准条目相互独立、无共享写入时，中间的区域检查可拆给多个全新检查实例并行执行——按 criteria 条目切分（不按文件切，避免漏掉跨文件矛盾），每个检查者对自己的条目负全责。**最终判定的汇总由主 Agent 或单一检查者负责**，对整体负责；并行检查者均未参与交付。小任务不拆（交接成本大于收益）。最终检查本身不并行——它是覆盖全部标准的整体判断。

**注意：没有固定的 `doc/` 目录（C-09）。** 给用户看的交付成果（报告、行程、设计稿、代码等）存放在用户偏好的位置，排版遵循用户习惯；任务目录只保存交付指针（deliverables.json）和证据。工作流内部文件是给 AI 和交接用的过程资产，不追求用户侧的排版美观。

**简单事项的极简形态**（例如一次临时脚本修改）：

```text
.fstar/tasks/<task-name>/
├── task.json                      ★ 阶段、状态、目标一句话
└── criteria.md                    ★ 两三条即可：期望结果 + 怎么验证
```

不强制生成 clarify.md 或 plan.md（此条仍是待评阅建议）。

## task.json 状态模型的扩展方向（C-17）

| 层 | 内容 | 与现状的关系 |
|---|---|---|
| 阶段 phase | 需求澄清 / 实施 / 验收 / 完成 | 沿用现有语义，放宽阶段内限制 |
| 运行状态 status | 推进中 / 等待用户 / 等待外部 / 暂停 | 新增；支持暂停恢复而不丢进度 |
| 工作项 work_items | 各步骤的完成、进行、受阻、取消 | 新增；细化 plan 的执行跟踪 |
| 下一步 next_step | 继续条件 + 动作 | 新增；跨会话接手的入口 |
| 事件日志 | 已有 append-only 机制 | 沿用，承载决定与依据 |

具体 schema 与现有 evidence/lease 字段的兼容是后续设计工作。

## 主 Agent 与后台协作的交付链（C-11/C-12/C-13）

```text
用户对话（主 Agent 持续在线）
   │  意图识别 → 判断作用范围（C-16）
   ├─ 后台：调研 / 落文档 / 执行 / 检查（带版本与依据派发）
   │     └ 返回结果先核时有效性，旧结果不覆盖新决定
   ├─ 交接节点1：约定形成 → 全新实例核对理解一致性
   ├─ 交接节点2：关键成果 → 限定范围独立检查
   └─ 交接节点3：最终交付 → 只读最终检查（对照 criteria.md
         + 用户关键原话），再向用户展示：达成项+证据 /
         未验证项 / 需用户判断项
```

最终检查只读（C-12）：检查者发现问题交回执行者修复，不自己改交付物。

## 经验循环与外部工具边界（C-18/C-19）

```text
工作流核心（自足）
  阶段语义 · 状态与事件 · 验收协议 · 经验的记录/调用/纠错/失效
        │
        ▼  能力接口（按能力定义，不按产品绑定）
  ┌────────────────────────────┐
  │ 会话管理（现 herdr 一类）   │ ←缺席时：主会话直接交互
  │ 能力分发（现 magpie 一类）  │ ←缺席时：宿主原生 skills/hooks
  │ 记忆存储（任一记忆系统）    │ ←缺席时：.fstar/knowledge/
  │ 调度触发（cron/事件类）    │ ←缺席时：仅手动驱动（第一版默认）
  └────────────────────────────┘
```

三个权威来源互不替代（C-19）：工具安装配置以能力管理系统为准；场景使用经验以经验库为准；本次操作授权以用户授权和规范为准。

## 与现有仓库结构的对应

| 现有 | 优化后 | 变化 |
|---|---|---|
| task.json 26 字段、phase、事件 | 保留核心，扩展 status/next_step 等运行层 | 兼容性影响待分析 |
| clarify.md / plan.md 固定要求 | 按需生成，模板改为质量规则+示例 | C-09 |
| acceptance/ 仅存 check 报告 | 增加 criteria.md，实施前确定 | C-13 |
| doc/prd+design 默认组合 | **移除 `doc/` 概念**：交付物按用户偏好存放（一次引导+习惯沿用），任务目录留 deliverables.json 指针；artifact_map/编辑协议/证据关联改为按“交付文件注册”工作 | C-09，依赖分析重点 |
| 四角色卡（research/editor/implement/check） | 打磨质量指导；check 最终验收改只读；editor 定位变为“编辑指定交付文件的指定部分”，与路径无关 | C-12，细节待设计 |
| routing.md 硬性最小循环 | 约束收缩为 C-15 少量硬规则 | 待重写 |
| magpie.py 直接分发 skills | 收敛为能力接口的适配实现之一 | C-14 |
