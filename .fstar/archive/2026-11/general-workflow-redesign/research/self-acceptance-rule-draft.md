# 开发任务自验收规则

> 用户审定确认（2026-11-21）：确认 但是如果后续开发任务如果涉及到扩展和修复的任务 规则需要一并去兼容

## 授权声明

用户原话（2026-11-21）：
> 我现在有个难受的点就是当前这个fstar工作流我没有办法自己去验收，只能信任你去验收，我觉得当前项目需要个自验收的全流程，以后开发完某项任务时都走这个自验收流程就代表我已经验收通过

用户审定确认（2026-11-21）：
> 确认 但是如果后续开发任务如果涉及到扩展和修复的任务 规则需要一并去兼容

本规则代表用户完成指定类别任务的验收。

## 适用范围

- 适用于：fstar 项目管理下的**开发类任务，含新功能、扩展（extension）、修复（fix）**。
- 完成于本规则激活之后的任务；不追溯激活前的任务。

## 准入门槛（全部满足才可自验收）

1. 任务有用户逐条确认过的 criteria.md（验收标准每条来自用户已确认的要求或澄清记录里的用户原话）。
2. criteria.md 每条标准的判定方式均为 machine（可由测试命令、独立 Agent 检查或来源核实客观判定）；含任何 user-judgment 条目的任务不得自验收。
3. 独立检查与最终只读检查均通过，检查者与所有交付者不同实例。
4. 证据新鲜：最终检查通过后交付文件未被改动（内容寻址核对）。
5. 无 failed / blocked / 未验证的验收条目，无未解决的 blocker。

## 执行程序（自验收时必须完整走一遍）

1. 逐条判定 criteria.md：每条给出判定结果与证据链接（测试输出、检查报告节、来源核实记录）。
2. 核对准入门槛五项，任一不满足 → 立即停止，任务转 waiting_user 等用户处理。
3. 全部通过 → 生成验收报告，存入任务目录 checks/self-acceptance.md，含：逐条判定表、门槛核对记录、引用的证据。
4. 以本规则完成验收（accept --rule），事件日志引用本规则路径与用户授权原话。
5. 下一轮对话主动向用户汇报本次自验收的结论与报告位置。

## 永不覆盖清单（本规则永远不适用，必须用户亲验）

- 版本发布、npm publish、git push 到远端、分支合并。
- 删除数据、破坏性变更、schema 迁移。
- 对外发布内容（文章、公告、公开仓库的 Issue/PR 回复）。
- 修改本规则自身或任何验收相关机制（routing 硬规则、accept 语义、evidence 校验）。
- 涉及密钥、账号、付款的操作。

## 防漂移约束

- 修改本规则文本必须重新经用户明确授权（learn 流程确认），旧版本引用即时失效。
- 自验收报告可随时被用户抽查；用户质疑任一报告时，该报告对应的验收结论重新回到待验收状态。
- 用户在任务进行中到场并表示要亲验时，该任务退出自验收资格。
