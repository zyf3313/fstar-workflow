# 工具维度：能力契约、分类器与绑定

状态：规划草案，2026-10-27。**不构成实现授权。**

本文件是 fstar 相对 Trellis 的**第 5 个自研增量**。用户 2026-10-27 提出：整体架构缺少「工具」维度；需要能扩展每个角色对应的模板 + skills + 工具概念；难点在于**每个人用的工具不同**，且**工具会不定时出现更好的替代**。

> **定位（2026-10-28 最小内核 + 扩展包定案）**：本文件描述的能力契约 / 绑定 / 分类器整体构成**「工具能力包」**——六个扩展包之一。它**不是 fstar 的底座**：未加载该包时，fstar 仍可用最小闭环走完「澄清 → 执行 → 基础检查 ↔ 修复 → 用户确认」，只是不走能力契约的降级路径。加载该包时默认整包加载、用户可裁剪其中能力，授权记 `task.json.extensions[]`（与本文件记录的 `task.json.capabilities[]` **分离**：前者记用户授权，后者记工具 provenance）。见父任务 `prd.md` §12、`design.md` §2.4。

来源：旧扩展项目 `personal-trellis` 的 10 篇指南（尤其 5 篇中近乎逐字重复的「能力发现与软安装」样板）、`README.md:199-217`（需求与长期资产）、`README.md:263-271`（工具推荐表）、`README.md:299-303`（能力不足判断矩阵）。

## 一、为什么这是独立的一层

Trellis 的工具是**写死的**：指南直接点名 CodeGraph / QMD / Exa / DBHub，hook 是固定 Python 脚本。工具换了就意味着偏离上游文档。

fstar 的做法是三段分离：

```
能力（capability）      稳定，fstar 定义，跨人不变
   定义 · 判定要点 · 降级路径 · 记录要求
        ↑
绑定（binding）         可变，用户/项目配置，随时可换
   能力 → 实际工具 · 作用域 · 授权状态 · 选择理由
        ↓
实际工具（tool）         外部事实，随时会变
   CLI / MCP server / 宿主 skill / 内置能力
```

**能力契约归 fstar，绑定归用户，工具是外部事实。**

这直接解决两个难点：

| 难点 | 解法 |
|---|---|
| 每个人用的工具不同 | 每人写自己的绑定，契约一个字不改 |
| 工具会不定时变化 | 只改绑定；契约的「推荐实现」可随安装包升级，但**不动用户已选绑定**（复用已定的「不覆盖用户修改」原则） |

### 与旧扩展项目的关系

旧项目的 5 篇重复样板（`code-search` / `database-access` / `knowledge-search` / `web-research` / `ui-design`）**不是 5 个工具的说明，而是 1 个横切机制的 5 次实例化**（其中 4 篇对应第一版的 4 个能力维度；`ui-design` 已移出工具层，见下）`legacy-assets-inventory.md` 曾建议「抽为 1 份共享 reference」——那是去重动作，方向对但定位低：它把机制消掉了，没把它立成架构维度。

本文件把那份样板升格为「能力契约集合 + 分类器」。

**8 步共同骨架（来自 `legacy-assets-inventory.md`，事实）**：

> 尊重用户已选工具 → 按能力而非名字评估 → 无 Adequate 等价物时推荐指定来源 → 展示精确动作与影响 → 逐作用域单独授权 → 三层验证（可发现 / 客户端加载 / 一次真实最小调用）→ 被拒则降级并说明缺口 → 不重复已拒请求

本文件是这套骨架的正式化。

### 第 5 个旧指南：`ui-design` 移出工具层（2026-10-27 用户确认）

旧项目的 `ui-design` 原本是 5 篇共享「能力发现与软安装」样板的一篇，**第一版曾把它列为第 6 个能力维度**。用户确认**移出工具层**——理由是「不是一个整体闭环核心要点」。

技术上的补充理由：它原来的判定要点（「有基线可继承；状态与交互完整」）描述的是**产物质量**而非**工具能力**，分类器据此无法判定一个工具是否属于该维度——判定要点写不成可判定条件，维度就不成立。

**尚未决定它最终去哪里**：

- 回到技能层/模板层？可选的 `fstar-ui-design` skill 已在技能层，模板 `ui-baseline` / `ui-feature` 已在产物层，工具层这一环可能本就多余。
- 以其他形式回到工具层？若将来要支持「UI 工具是否存在」这类探测，需要重写判定要点。
- 还是整体不做？

**定位待后续讨论**，第一版不实现。

**第一版即 5 个维度。** 这是「轻量化」的落点——比旧项目的 10 篇少一半，覆盖了真正依赖外部工具的核心闭环场景。

## 三、能力契约格式

每个维度一份契约文件（安装包内 `capabilities/<id>.md`）。

```markdown
# 能力：代码结构检索
id: code-structure
适用角色: research / implement / check

## 能力定义
能回答「X 在哪定义」「谁调用它」「改这里影响什么」这类结构问题。

## 判定要点
- 支持符号级定位（定义 / 引用 / 影响面）
- 结果可追溯到 文件:行
- 能区分「符号不存在」与「工具没索引到」

## 验证方法（三层）
1. 可发现：绑定目标在本机存在
2. 客户端加载：能列出符号，不报未索引
3. 最小调用：对一个已知符号查一次定义，结果与源码一致

## 推荐实现（用户可覆盖并附理由）
CodeGraph / LSP

## 常见不合格实现
纯文本搜索 → 只能定位字面量，属降级不是替代

## 降级路径
无法回答影响面 → 明确说明该缺口，不用字面量结果冒充结构结论

## 记录要求
在 task.json 的 capabilities[] 与检查报告记录 capability + 实际工具 + 版本/来源
```

**「判定要点」是整套机制的支点**——它让「用 CodeGraph 还是别的」变成可判定的事，而不是口味问题。

### 契约 vs 绑定的职责

| | 能力契约 | 绑定 |
|---|---|---|
| 归谁 | fstar（安装包内） | 用户 / 项目 |
| 回答什么 | 「这个能力要满足什么」 | 「用什么满足」 |
| 变更频率 | 随安装包升级（低） | 随时（高） |
| 是否可被用户覆盖 | 可（用户目录同相对路径覆盖） | 就是用户的 |

## 四、分类器

用户核心诉求：**有个分类器，把本机现有工具归到维度下，处理特定维度时直接用。**

### 分类由 Python 实现，不用 AI（2026-10-27 用户确认）

用户提出分类器用 Python 写而非交给 AI 判断，理由是**浪费 token 且初始化慢**。已采纳，并补充两条更硬的理由：

| 理由 | 说明 |
|---|---|
| **确定性** | 同样输入必得同样结果。AI 分类每次可能不同 → 绑定漂移、diff 噪声、无法写回归测试 |
| **可测试** | 能写单元测试。AI 分类只能靠人工判断「这次分对了没有」 |
| **零延迟** | hook 在 SessionStart 和每轮 UserPromptSubmit 都跑，AI 往返会让每轮都变慢 |
| **可版本化** | 分类规则进 git，能 review、能回滚。**基础设施的输出不该由非确定性组件产生** |

「AI 永不进入分类路径」是硬约束。AI 仍可出现在两处，均**不在初始化热路径**：解释绑定提案的自然语言部分；判定「工具自述完全缺失的新 MCP server」这类真模糊情形。

### 三层结构

```
┌─ L1 存在性探测 ────────────────────────────────────────────────┐
│ 扫描本机：PATH 可执行文件 · MCP server 列表 · 已装 skill 目录  │
│ 产出候选清单（工具名 + 类型 + 版本）                            │
│ 不做判断，只做清点                                            │
└──────────────────────────────────────────────────────────────┘
                            ▼
┌─ L2 能力特征匹配 ──────────────────────────────────────────────┐
│ 对每个候选，按「这个工具能做什么」判定它属于哪些维度            │
│ 来源：工具自述（--help / MCP tool 列表 / skill description）   │
│ 不是靠名字匹配，是靠能力描述匹配                              │
└──────────────────────────────────────────────────────────────┘
                            ▼
┌─ L3 绑定与验证 ────────────────────────────────────────────────┐
│ 生成绑定提案 → 用户确认 → 写 tools.yaml                        │
│ 三层验证：可发现 → 客户端加载 → 一次最小真实调用              │
└──────────────────────────────────────────────────────────────┘
```

### L2 的内部顺序：注册表 → 通用探针 → 手动

**Python 不调用模型，那它凭什么知道某个工具属于哪个维度？** 知识必须落在某个地方。这直接撞上核心难点——**工具会不定时冒出来**。

三处放法与取舍：

| 方案 | 知识在哪 | 新工具怎么办 | 精度 |
|---|---|---|---|
| **声明式注册表** | 安装包内 `registry/<tool>.yaml` | 要等 fstar 发版才认识 | 高 |
| **维度级通用探针** | 每个能力契约里的探测模式 | 自动能抓到一部分 | 中 |
| **用户自写注册** | `~/.fstar/tools/registry.d/` | 用户自己加 | 取决于用户 |

**已确认采用前两者叠加、按序使用**（2026-10-27 用户确认）：

```
L1 探测    Python 扫 PATH / MCP 配置 / skill 目录 → 候选清单（纯文件系统操作）
              ↓
L2a 注册表  已知工具 → 能力维度，强匹配（精确、可 review）
              ↓
L2b 通用探针 按维度的探测模式试未注册工具（中等召回）
              ↓
L2c 残渣    两个都没命中的 → 列为「未分类候选」，附工具自述
```

**L2c 的处理方式：用户手动绑一行。** 不引入 AI 辅助分类层。理由：

- 日常路径上 L2c 通常为空——只有真出现全新工具时才有事。
- 让用户对「这个新工具属哪个维度」做一次判断，比让 AI 猜一次更可控，且判断结果直接成为用户自己的绑定记录（符合「绑定归用户」）。
- 注册表与探针都能在后续 fstar 版本里补上这个工具的规则，届时它自动升到 L2a/L2b——**不自动改绑定**，只提议。

### 为什么必须分三层

旧项目已有实证（`knowledge-search.md` 的 Verified baseline、`README.md:299-303` 的判断矩阵）：

| 误判 | 实证 |
|---|---|
| 「有 CLI 就等于能用」 | QMD 可执行文件在 ≠ 集合新鲜 ≠ 检索质量达标 |
| 「有索引目录就等于覆盖全」 | CodeGraph 存在 ≠ 当前仓库已索引 ≠ 内容新鲜 |
| 「有 MCP 就等于认证成功」 | 发现 Exa/`gh` ≠ 认证成功 ≠ 私库权限 ≠ 页面可读 |
| 「有客户端配置就等于连得上」 | DB 配置存在 ≠ 指定数据源连接 ≠ 只读约束 ≠ 查询成功 |

**L1 只回答「在不在」，L2 回答「能干什么」，L3 回答「这次真能用吗」。** 缺 L3 会把上面这些误判带进工作流。

### L2 怎么判断「能干什么」

不写死每个工具的规则，而是**问工具自己的自述**：

| 工具类型 | 能力自述来源 |
|---|---|
| CLI | `--help` 输出、man page |
| MCP server | 暴露的 tool 列表 + description |
| 宿主 skill | SKILL.md 的 `description` 字段 |
| 内置能力 | 宿主已声明的能力清单 |

拿这些自述去和维度的**判定要点**匹配。例：维度 1 要「符号级定位」，CodeGraph 暴露 `codegraph_context / search / callers / impact` → 命中；`rg` 只有字面量匹配 → **落到维度 1 的降级路径，不占主绑定**。

匹配走两级：**L2a 注册表**给出已知工具的精确结论（`registry/codegraph.yaml` 声明其暴露的能力 → 维度映射）；**L2b 通用探针**用每个能力契约自带的探测模式去试未注册工具。

```yaml
# 安装包内 registry/codegraph.yaml（随 fstar 发布）
tool: codegraph
kind: cli
detect:
  - which: codegraph
capabilities:
  - id: code-structure
    match: strong
    basis: "暴露 codegraph_search / callers / impact，属符号级"
```

```yaml
# 安装包内 capabilities/code-structure.md 的探针段（维度级）
probes:
  - name: "暴露符号检索能力"
    match_any: ["codegraph_search", "codegraph_callers", "codegraph_impact"]
  - name: "输出可追溯到 文件:行"
    pattern: "\\w+\\.(py|ts|js|go|rs):\\d+"
```

注册表是**精度**，探针是**召回**。两者都进版本控制，可 review、可回滚。

### 三层验证也能 Python 化

原先设想的「一次最小真实调用」一度被认为需要 Agent 参与。实际上大部分可以写成确定性脚本：

| 验证层 | 能否 Python 化 | 做法 |
|---|---|---|
| 可发现 | ✅ | `shutil.which` / 检查 MCP 配置 / 解析 skill frontmatter |
| 客户端加载 | ✅ | CLI 跑 `--help` 看是否报错；MCP 查客户端是否列出该 tool |
| **最小真实调用** | ✅ **大部分可以** | 取一个已知符号，跑一次工具，比对输出 |

「已知符号」这个锚点由脚本从项目里挑（如从源文件抽一个符号名），然后验工具返回的 `file:line` 是否真的对得上。**CodeGraph 能不能索引这个仓库，可以用脚本判定，不需要 AI。**

只有一种情况离不开 AI：**工具自述完全缺失或不准确的全新 MCP server**——这时才需要人/AI 去读它的文档判断归属。

### 性能：分类器不进每轮热路径

| 时机 | 做什么 | 开销 |
|---|---|---|
| `fstar init` / 显式 `fstar tools scan` | 完整 L1 + L2 | 一次性，秒级 |
| `session-context` hook | 只查已绑定工具是否还在（`shutil.which`）+ `detected_at` 是否过期 | 微秒级 |
| `turn-context` hook | 不碰工具 | 零 |

`session-context` 只在发现「绑定失效」或「探测结果过期」时才提示，其余时候静默。

### 探测结果格式

```yaml
# ~/.fstar/tools.yaml
detected_at: 2026-10-27
tools:
  - tool: codegraph
    kind: cli                    # cli | mcp | skill | builtin
    version: "0.4.1"
    capabilities:                # L2 判定结果
      - id: code-structure
        match: strong            # strong | weak | none
        basis: "暴露 codegraph_search / callers / impact，属符号级"
      - id: code-text
        match: weak
        basis: "含字面量检索，但非其主打"
  - tool: qmd
    kind: cli
    version: "2.8.3"
    capabilities:
      - id: knowledge-retrieval
        match: strong
        basis: "BM25/FTS 集合检索 + 可选语义"
  - tool: rg
    kind: cli
    capabilities:
      - id: code-text
        match: strong
      - id: code-structure
        match: weak
        basis: "仅字面量，命中降级路径"

bindings:                         # 用户确认后才写这里
  code-structure: codegraph
  knowledge-retrieval: qmd
  code-text: rg
  data-access: null              # 未绑定 → 走缺口语义
```

**`detected_at` 让探测结果有时效。** 工具装了新的、删了旧的、换了版本，下次扫描能看出差异——这就是「不定时出了个更好用的工具」的应对方式：**不自动换，但要能发现并提议。**

## 五、三个挂钩点

用户要求：需要出 hooks、初始化、对应 skills 专门处理这些事。

| 挂钩点 | 落点 | 做什么 |
|---|---|---|
| **初始化** | `fstar-init` | 项目接入时跑一次 L1 探测 + L2 匹配，生成绑定提案；用户确认后写 `~/.fstar/tools.yaml`（用户级）或 `.fstar/tools.yaml`（项目级） |
| **Hook** | `session-context` | 会话启动时检查 `detected_at` 是否过期、有无新增可用工具 → 有变化时**提示**「检测到新工具 X，可能匹配维度 Y」；不自动改绑定 |
| **Skill** | 新增 `fstar-tools` | 处理具体维度时：查绑定 → 按需验证 → 调用 → 记录用了哪个 → 缺口时按契约降级 |

### `fstar-tools` 技能契约

| 项 | 内容 |
|---|---|
| 触发 | 需要某维度能力；初始化时；发现绑定失效；用户要换工具 |
| 输入 | 维度 ID、任务意图、当前绑定与探测结果 |
| 输出 | 实际调用的工具 + 版本记录；绑定提案；缺口报告 |
| 引用 | `references/contracts.md`（5 个维度的判定要点与降级路径）、`references/probe.md`（L1/L2 检测法）、`references/bindings.md`（绑定与版本记录格式） |
| **不负责** | 自动安装任何工具；自动改绑定；替代 `fstar-check` 的验收判断 |

### 硬边界：不自动安装

旧项目原则：**发现工具缺失不等于有权自动安装**。安装要单独授权、单独确认范围（全局可执行文件 / 集合创建 / 模型下载各自独立授权）。

本设计保留该原则：**fstar 只提议，不装。** 缺口的正确行为是「说明缺口 + 给出建议来源 + 走契约降级路径」，不是「顺手装上」。

### 记录要求（接到已有设计）

> **修正（2026-10-27 数据格式审计）**：Trellis 实际只有 `implement.jsonl` / `check.jsonl` 两个清单文件，**不存在 `context.jsonl` / `history.jsonl`**（`grep -rn` 零命中）。此前此处写错。fstar 不凭空造这两个格式。

| 位置 | 记什么 |
|---|---|
| `task.json` 的 `capabilities[]` | 本任务用过哪些能力维度 + 实际工具 + 版本/来源（provenance） |
| `task.json` 的 `evidence[]` | 检查/验证产出的证据，含指纹与 stale 状态 |
| `acceptance/check-<n>.md` | 实际使用的能力 / 工具 / 版本（人读摘要） |
| `~/.fstar/tools.yaml` | 工具变更事件（`detected_at` 与 `history` 段），机器读 |

这条正好落在 `hooks-skills-templates.md` 已有的那句「在任务上下文清单或检查报告中记录实际使用的能力及版本/来源」上。

详见 `research/data-formats.md` §二与 §五。

## 六、存储落点

| 路径 | 内容 | 归属 | 入库 |
|---|---|---|---|
| `~/.fstar/tools.yaml` | 能力 → 工具的选择（绑定） | 用户 | ✅ |
| `~/.fstar/tools.local.yaml` | 本机路径、验证状态 | 本机 | ❌ |
| `.fstar/tools.yaml` | 项目级覆盖 | 项目 | ✅ |
| `~/.fstar/runtime/tool-status.json` | 验证结果（事实） | 运行时 | ❌ |
| `~/.fstar/tools/registry.d/*.yaml` | 用户自写的工具注册条目 | 用户 | ✅ |
| 安装包 `registry/*.yaml` | fstar 维护的已知工具注册表 | 安装包 | ✅ |
| 安装包 `capabilities/*.md` | 5 个能力契约（含判定要点与探针） | 安装包 | ✅ |

**绑定是配置（可入库、跨机共享），验证状态是事实（不入库）**——与已定的 `config.yaml` / `config.local.yaml` 分法一致。

优先级：**项目级 > 用户级 > 安装包默认推荐**（与已定的「项目规范优先于全局」同构）。

注册表同理：用户 `registry.d/` > 安装包 `registry/`。用户自写条目用于「装了新工具但 fstar 还没发版认识它」的情况。

## 七、遗留难点

| # | 难点 | 现状 |
|---|---|---|
| 1 | 能力边界怎么划 | 5 个维度的划分（2026-10-27 用户确认）；`ui-design` 的定位待后续讨论 |
| 2 | 判定要点怎么自动验 | 第三层验证已可脚本化（见上），但有成本和副作用 |
| 3 | 工具 API 漂移 | 绑定还在但工具改了接口；客户端加载那层能发现一部分，不能全兜住 |
| 4 | **provenance 不可信** | Agent 声称用了 CodeGraph、实际用了 grep，检查报告无法自证。**这条最难解**，短期只能靠检查环节核对 |
| 5 | 能力缺失时的体验 | 缺口报告写给谁看、要不要阻塞任务、是否提醒补绑定 |
| 6 | 分类器的判断依据来源 | L2 依赖工具自述质量；自述不全或过时时会误判。**注册表 + 探针双轨缓解，但消不掉** |
| 7 | **注册表的新工具滞后** | 新工具出现 → L2b 探针可能抓到并提示，但要等 fstar 发版才进 L2a。用户可先写 `registry.d/` 自救 |
| 8 | 探针的误报 | 通用探针按模式匹配，可能把偶然命中模式的工具判为强匹配。**缓解：探针命中一律标 `weak`，升为 `strong` 必须经注册表或用户确认** |
