# fstar Skills 细节能力清单与缺口分析

状态：待评审草案。不授权实现。下方历史表为早期版本，不再作为实施依据；以本文件顶部最新契约与 `policy-decisions.md` 为准。

## 最新职责覆盖（2026-10-29 全量核对完成）

- `fstar-init`（2026-10-29 补充）：已有项目先检索实际类型、技术栈、模块和权威文档，再规划规范维度/主题职责/目录/索引；零起步缺参考时询问项目内容、技术栈与关键约束，复用已有明确答案，不擅自定选型。learn 按此结构维护，优先更新已有主题，无归属再说明新增/调整原因。读取策略已确认：先掌握全局，再完整读取所有适用主题及上下游/共享契约，范围不明确扩大读取，新增依赖补读。init/learn 产出的规范需结构化、简洁明确，考虑 token 成本，避免长篇叙述及重复正文，同时保留必要条件和例外；写作参考 Trellis 既有沉淀规则，不另加多栏目固定骨架。用户确认 `specs/` 默认英文，项目配置可覆盖，init 与 learn 一致遵循；任务文档默认中文不变。

## 执行细则补充（2026-10-29 已确认）

- init：接入清单核验（入口/主题/引用/背景来源）；已有内容读取引用为主，修改需说明范围并确认；项目接入时跑一次工具探测与绑定提案，用户确认后写 `tools.yaml`，不自动写绑定不自动安装；工具能力包未启用时接入仍可完成。
- continue：恢复前核实状态/产物/执行者/证据新鲜度，不一致先说明差异；不做巡检提醒（巡检只归 archive，暂缓去重统一维护）。
- learn：写入原子完成（正文+索引+引用）；先判断是否值得沉淀（未来用到/项目内 vs 跨项目/已有权威承载/已验证事实）；发现知识冲突先警示，确认后再更新；文件重命名需依据并同步全部引用。

- `fstar-clarify`：沟通需求和技术方案，明确结论/修改范围/未决项；需要落评审稿时调用 doc，不直接写 prd/design，不生成 plan。
- `fstar-doc`（2026-10-29 最新范围）：仅维护任务 doc/ 下的文档，目前 prd/design，后续随该目录的文档类型扩充指引。核心是按模板规范生成内容；具体写作派给后台 editor 子 Agent，主 Agent 继续讨论。可依据阶段性明确结论编写，未决项显式保留；讨论结束后收齐稿件，按最终结论整体核对，沿用 check 的独立文档检查职责，修正后交用户评审确认。取代「小改自己做、大改才派 editor」建议；不得以旧稿覆盖新结论或并发覆盖同一文件。不自行裁定需求、批准或扩大授权。其他产物由各自 skill/角色维护：clarify 自行维护任务根 `clarify.md`（名称已确认），plan 写 plan.md，check 写检查报告，research 写调研，learn 写获授权的沉淀内容。程序状态仍通过命令维护。
- `fstar-plan`：确认后自动生成/刷新 plan.md，含来源、优先级、依赖、可并行条件、实施项与验证方法。
- `fstar-check`：实施交付后直接审查并编写/补充测试代码、实际运行、报告结果；不生成 test-cases.md，不以用例审批为前置条件。独立文档一致性检查仍由 check 负责，共享检查清单。测试预期来自需求；2026-10-29 用户确认 check 可直接修改本任务范围内的生产代码和测试代码，修复后重新验证并报告。撤销下方历史表的禁改生产代码与必须交 implement 限制；需求/方案变化仍返回讨论。实施与检查角色分离、最终用户验收保留。
- `fstar-continue`：当前任务进度与恢复，不承载回忆；回忆/归档查询归主路由。无独立 recall 或 ui-design skill。
- `execute/check` 流程优化（2026-10-29 已确认）：每轮检查明确 plan 项、基线、范围、必需验证及结束条件；主 Agent 协调实施→检查的写入交接，同一范围不并发修改，结果绑定检查版本；修复后按影响复查，最终整体检查；重复失败无进展或环境阻塞及时返回原因/尝试记录，必要时 debug。检查报告呈现各阶段耗时和重跑次数，plan.md 展示当前动作及阻塞摘要。多 check 并行、恢复原检查者留作后续优化。
- `fstar-archive`（2026-10-29 更名，原 fstar-finish）：中文名「任务归档」；归档前的用户验收、收尾检查及知识沉淀衔接保留，沉淀候选暂缓或不保存不阻塞归档。归档完成后巡检当前项目其他长期未归档任务，汇总时间依据、状态及缺失步骤，区分可归档与缺验收/检查/停滞，支持暂缓去重，不阻塞、不自动归档其他任务。详细内容继续审阅。下方历史 finish 名称以此为准。
- `fstar-learn`（2026-10-29 已确认触发）：用户要求记住、用户纠正、讨论长期约定、开发可复用发现、排障根因/check 重复问题、旧知识失效冲突、收尾归档、恢复相关未处理候选。过程中识别、合适节点集中呈现；主动要求当场处理，明确授权不重复确认，拒绝/暂缓不重复催促。hook 只触发提醒，learn 判断去重归口并按授权保存；优先更新已有权威知识与索引，注明适用条件。沉淀候选不阻塞归档。
- learn 执行方式（2026-10-29 已确认）：主 Agent 忙时派后台通用子 Agent，空闲且小改时直接执行，复杂整理优先后台。候选整理不擅自写成生效知识；已确认写入按授权内容/归属/范围执行。同文件写入合并或排队，收到成功结果再报告已记录；不新增专用 learn 角色，editor 仍专注 doc/。
- debug / help / tools（2026-10-29 已确认）：debug 反复失败或根因不明时介入，借鉴 break-loop 根因分类与贝叶斯框架，按根因层级返回对应环节，结论经 learn 沉淀；help 依据安装包入口索引与当前配置按需回答，只读不改状态；tools 沿用查绑定→三层验证→调用记录→缺口降级，init 首次探测。12 个 skill 内容至此全部逐项核对完成。
- research 与 check 报告（2026-10-29 已确认）：research 按需生成（个别事实进 clarify.md 带来源；多来源对比/探测/协议调研/方案取舍才建文件；结论与详细依据不重复）。check 报告 acceptance/check-<n>.md 采 Trellis 角色卡报告要点并补范围基线、五态结论、修复内容、耗时与重跑次数、版本指纹与证据影响，因承担证据职责不能直接照抄。
- 当前共 12 skills：init / clarify / doc / plan / execute / check / continue / archive / debug / learn / help / tools。测试评审包暂缓，基础检查仍属最小闭环。

## 前置修正（两处此前的错误）

### 1. 调研是 Agent，不是 Skill

`.trellis/workflow.md:237` 明确：`trellis-research` 是 sub-agent type，**不存在同名 skill**。此前把它映射成 `fstar-research` 技能是错的。

正确结构：

```
Agent（角色：谁干、写到哪、禁止什么）
  └─ 调用 Skill / MCP（用什么能力）
       └─ 产出 research/<主题>.md
```

调研 Agent 的工具列表本身包含 `Skill`，workflow 也写明调研可用「任何可用工具（MCP、skills、web search）」。因此**能力发现是调研 Agent 的既有动作**，不需要独立技能，也不需要索引层。

### 2. 技能常驻成本：已按宿主实测核实（2026-10-27）

此前「预算约 2,720 tokens、描述被丢弃」的表述**不准确**。在 Claude Code 2.1.311 二进制中核实后修正：

| 项 | 事实 |
|---|---|
| 预算单位 | **字符**，不是 token。`预算 = 上下文 token × 每 token 字节数(回退 4) × skillListingBudgetFraction(默认 0.01)` |
| 本机实际预算 | `272000 × 4 × 0.01 =` **10,880 字符** |
| 超预算的后果 | 描述**降级为 name-only**，skill 不被移除——但模型无描述可匹配，**自动触发失效** |
| 分配规则 | 内置 skill 优先保留完整描述；其余按 `usageCount × max(0.5^(天数/7), 0.1)` 贪心分配，**从未用过的 skill 分数 0，平局全输** |
| 本机实测 | 338 个 skill；**仅名字就占 6,247 字符（预算的 57%）**；描述共 90,930 字符 |
| `skillOverrides` | 真实设置项，取值 `on`/`name-only`/`user-invocable-only`/`off`，**按名精确匹配，无通配符**；后两者消耗 0 清单字符 |
| `disable-model-invocation` | SKILL.md frontmatter 布尔字段，为 true 则**消耗 0 字符**且模型不可调用 |

**结论不变但理由更硬**：fstar 不做技能索引层——宿主已提供足够的预算控制手段（`skillOverrides` / `disable-model-invocation` / `skillListingBudgetFraction`）。但**光靠「描述写短」救不回来**：339 个 skill 的名字就吃掉一半预算，fstar 必须靠「首次调用写入 `skillUsage`」才能赢得分配。

完整机制、实测数据与 fstar 的 7 条缓解措施见 `research/data-formats.md` §4.1。

## 一、Agent 角色（4 个）

| Agent | 触发 | 输入 | 输出 | 禁止 |
|---|---|---|---|---|
| `research` | 需要外部事实、代码定位、选型依据 | 调研问题、任务路径 | `research/<主题>.md`，每个主题一份 | 改代码、改 spec、写其他任务目录 |
| `implement` | 实施或修复 | PRD、design、implement、context 清单、specs | 代码变更、实施交付说明 | git commit/push/merge、判定任务完成 |
| `check` | 实施交付后进入 `checking`：先据已写代码 + prd 生成用例草案；用户 `approved` 且指纹新鲜后执行 | 交付物、prd 条目、代码、`doc/test-cases.md` 稳定 ID/批准范围/指纹、审批证据、specs | 逐条目用例与场景链用例草案；范围内单元/集成测试、实际运行、证据映射；失败 F-xxx 可附不自动应用的 unified diff 建议补丁 | 改生产代码、未批准即编写测试、替用户验收、扩大范围重构 |
| **`editor`**（2026-10-27 新增） | 讨论/评审中要定点修改文档 | 修改要求、**被指定的文件与条目** | 改后的 `doc/*.md` + diff 摘要 | 改被指定范围外的内容、增删条目 ID、自行决定评审结论、改代码 |

**`editor` 不能用 `implement` 代替**：`implement` 带写代码权限与「完成实现」的语义，派它改文档会越界。专职角色的主要收益是**上下文卫生**——主 agent 只拿到「改了哪几条」的摘要，不吃进整篇文档。

角色文件只写权限、输入契约、交付格式。**方法细节放 skill reference，不重复写两遍。**

## 二、Skill 清单（共 13 个：核心 4 自动触发 + 协商路由 8 + 可选 1）

**skill 分层（2026-10-28 定案，配合宿主 listing 预算）**：

- **核心 4 个，自动触发**：`fstar-execute` / `fstar-check` / `fstar-debug` / `fstar-help`——支撑最小闭环，description 面向自动匹配，保持完整描述常驻预算。
- **其余 9 个，协商路由**：`fstar-init` / `fstar-clarify` / `fstar-continue` / `fstar-finish` / `fstar-learn` / `fstar-recall` / `fstar-tools` / `fstar-doc` / `fstar-ui-design`（可选）——在对应扩展包被用户同意后由主 Agent 显式调用，不依赖 description 自动匹配；可配 `skillOverrides: name-only` / `user-invocable-only` 降 listing 占用（用户仍可 `/fstar:xxx` 手动调用）。skill 总数仍 **13** 不变。

通用约定：每个 skill 只在 `SKILL.md` 放触发条件、步骤骨架、参考路由；详细内容进 `references/`。不预加载全部 reference。

### 1. `fstar-init` — 项目接入与规范整理

| 项 | 内容 |
|---|---|
| 触发 | 进入未接入项目且确定要持续开发；用户要求整理/刷新项目规范 |
| 输入 | 现有 README、docs、代码结构、已有规范 |
| 输出 | `.fstar/index.md`、`config.yaml`、`.gitignore`；按需 `specs/` 初稿 |
| 引用 | `references/onboarding.md`、`references/spec-bootstrap.md` |
| 不负责 | 创建任务、写 PRD、全仓库扫描生成空规范 |
| 前置 | 无。小事不接入，直接用用户级能力 |

要点：已有 `docs/` 优先引用不复制；**不预建 frontend/backend 分层——规范按主题归口**（每个主题记录标识·适用范围·权威路径·何时读；新增规范先归入已有主题，无归属才提议新增并说明理由）；模板占位符不得留空。

### 2. `fstar-clarify` — 需求澄清与规划

| 项 | 内容 |
|---|---|
| 触发 | 需求不清、新功能、范围变更、需要技术设计（规划评审包获同意后由主 Agent 路由；该 skill 本身属协商路由层） |
| 输入 | 用户描述、已有产物、research 结果、项目 specs |
| 输出 | `doc/prd.md`（评审稿·需求，启用规划评审包后必有）；复杂任务加 `doc/design.md` + `implement.md`；需要时**子任务树** |
| 引用 | `references/clarification.md`、`references/design-profiles.md` |
| 不负责 | 实施、写代码、自行把状态推到 implementing |
| 状态 | `drafting → planned`（需需求评审稿已评审 + 用户确认启动） |

**子任务拆分归属此技能**：一个完整需求 = 一个主任务，子任务放 `tasks/<主任务>/subtasks/`，目录体现归属。小任务不拆。

**命名（2026-10-26 用户确认）**：原名 `fstar-plan`，改为 `fstar-clarify`。理由：

1. `plan` 在项目管理语境有歧义——会被读成「排期 / 排优先级」，与本技能实际职责（把用户的一句话收敛成有验收条件的 `prd.md`）不符。
2. 其余 9 个通用技能全是动词（`init / execute / check / continue / finish / debug / learn / recall / help`），`plan` 是唯一纯名词。
3. 与 Trellis `trellis-brainstorm` 语义重叠。fstar 已把「探索」拆给 `research` Agent，本技能只干收敛那一半；名字叫 `clarify` 能让与 research 的分工在名字上就成立。
4. 已排除的候选：`fstar-draft`（`draft` 带「还不正式」的暗示，与可能是正式产物的 `prd.md` 冲突）、`fstar-scope`（英文 scope 在代码里指作用域，会与 code scope 混）、`fstar-spec`（撞项目级 `specs/` 目录）、`fstar-design`（撞 `design.md` 产物名，也撞 UI design）。
5. 触发准确度主要由 skill frontmatter 的 `description` 决定，name 几乎不参与宿主匹配；本项决策的权重在「给人读」和「手动调用 `/fstar:xxx`」，改名成本此时为零（尚未实现），等装到机器上再改就要动 11 个 SKILL.md 的 frontmatter 和用户的 `skillOverrides`。

注意：`fstar-clarify` 也会产出 `doc/design.md` 与 `implement.md`（复杂任务），但这两份是**澄清收敛的副产物**，不是独立技能职责；靠 description 说明即可。

### 3. `fstar-execute` — 实施与变更传导

| 项 | 内容 |
|---|---|
| 触发 | `planned` 且用户确认启动；实施中收到需求变更 |
| 输入 | PRD/design/implement、context 清单、specs、rules |
| 输出 | 代码变更、实施交付、task.json 事件记录 |
| 引用 | `references/before-dev.md`、`references/dispatch.md`、`references/changes.md`、`references/capability-discovery.md` |
| 不负责 | 用户验收、归档、判定自己完成 |
| 状态 | `planned → implementing` |

含三件事：开工前读规范并确认变更边界；派发实施者并在检查点回收；中途变更时更新任务依据、通知执行者、标记受影响证据。

### 4. `fstar-check` — 检查与证据

| 项 | 内容 |
|---|---|
| 触发 | 实施交付；修复后复查；需求变更导致证据失效 |
| 输入 | 已写好的代码、交付物、prd 条目、用户提供/修改的用例（如有）、用户批准证据、当前版本/指纹、specs、测试命令 |
| 输出 | 准备阶段：开发完成后生成 `doc/test-cases.md`，含逐条目用例与场景链用例；执行阶段：逐条目用例落单测、场景链用例落集成测试，实际运行并写逐用例映射；失败 F-xxx 可附绑定问题/用例/行号的 unified diff 建议补丁（不自动应用） |
| 引用 | `references/testing.md`、`references/document-consistency.md` |
| 不负责 | 替用户验收、修改生产代码、把用例生成或文件存在当成测试通过、把检查通过当作任务完成 |
| 状态 | `implementing → checking`；用例未获用户 `approved` 或指纹过期时只做准备/重审；确认且新鲜才派 check 按稳定 ID 编写/补充单测（必要时集成测试）并运行；生产缺陷 `checking → fixing` 交 implement 修复后复查；实际通过且审批/证据仍新鲜才 `→ awaiting_acceptance` |

用户可直接提供/修改用例，但不能从文件存在推断批准；用户口头确认时 Agent 代记 `source: conversation`、原话引用与当时指纹。此前把用例草案放在规划/clarify 阶段的方案已作废。缺陷修复后补对应回归用例。修改用例使关联 review/check evidence stale；回收时重核指纹。建议补丁只供 fixing 轮 implement 采纳、改写或说明理由否决，check 不得自动应用。

### 5. `fstar-continue` — 恢复与巡检

| 项 | 内容 |
|---|---|
| 触发 | 用户说继续/恢复；打开项目；存在多个候选任务 |
| 输入 | `task.json`（含 events[]）、租约、执行者状态、提醒记录 |
| 输出 | 真实进度摘要、下一步建议、**归档巡检结果** |
| 引用 | 无（或极少量） |
| 不负责 | 自动推进到验收、自动归档、静默重复派发 |

必须区分三种在途情形：租约活跃（报进度不重派）、租约失效（提示继续/重派/放弃）、无租约（正常推进）。**归档巡检在此收敛**，不另设 hook。

### 13. `fstar-doc` — 文档维护与一致性（2026-10-27 用户确认新增）

| 项 | 内容 |
|---|---|
| 触发 | 讨论中产生文档修改要求；评审意见要落到文档；用户说「把 X 改成 Y」（**定点修改**） |
| 输入 | 修改要求、`doc/` 当前版本、相关评审记录 |
| 输出 | 改后的 `doc/*.md`；回读校验结论；改了哪几处的摘要 |
| 引用 | `references/doc-consistency.md`；命令 `fstar doc check` / `fstar evidence invalidate --file` |
| 不负责 | 判断需求对错；写代码；自行决定评审结论；增删条目 ID（除非用户明确指示） |
| 状态 | 不改任务 phase；只影响证据与评审记录的有效性 |

**流程**：判定改动量 → 小改自己做 / 跨文件或大段重写则派 `editor` 子 agent → **回读校验**（语义槽位齐否、条目 ID 是否稳定、关联是否断、图文是否一致）→ 更新指纹与 stale → 安排变更传导 → 回报改了哪几处。

**为什么不能并进 `clarify` / `check`**：那两者的触发词是「需求不清 / 新功能 / 范围变更」与「实施交付 / 修复后复查」。用户说「把 R-003 的异常分支改成先落库再发消息」是**定点修改**，匹配不上任何一个，会漏触发。一致性校验是横切关注点，分散在两处各写一遍会漂。

**skill 数量上限 13 个**——listing 预算吃紧，且 fstar 的 skill 只有被调用过一次（`skillUsage` 分数 > 0）才能在贪心分配里赢过那批从未使用的 skill。

### 缺口的处理建议

**8. 轻重形态** — 2026-10-28 起不再是「轻量 vs 正式判定」：轻量 = 未加载扩展包的最小闭环；扩展信号触发协商（见上节）。

**9. 归档巡检** — 已在 `fstar-continue` 中收敛。需补：巡检项清单、去重与暂缓键、提醒文案需说明缺失项（未归档 / 证据过期 / 子任务未完成）。

**10. 提交与发布** — 建议放 `fstar-finish` 的前置步骤，或独立为 `fstar-ship`。Trellis 把它放在 Phase 3.4（finish 之前），因为「归档」和「提交」是两件事。**倾向不新增技能，在 finish 内分成「提交 → 验收 → 归档」三段。**

**11. 回滚** — 建议并入 `fstar-execute` 的异常路径，不单列技能。触发：检查反复失败且修复代价高于重来、或需求被撤销。

**12. 证据失效** — 权威归核心命令：计算指纹并按稳定 ID/依赖标 stale；`doc-change` 与各 skill 调同一入口。用例变更即使在 drafting 也使已有 review/check evidence stale；派发、恢复与结果回收重算校验，不能只靠 check 自觉或 hook 命中。

**13. 租约接管** — 明确写在 `fstar-continue`：检测到他人活跃租约时只读不写；接管需记录作废原因与新 owner。

**14. 产品升级** — 不放进工作流技能。由 CLI 的更新机制处理，`fstar-help` 提供说明。

## 最小闭环与扩展包（2026-10-28 定案，取代旧「轻量任务规则」）

> **决策轨迹**：本节此前为「轻量任务规则（已确认）」——轻量/正式二分类 + 4 条自动升级规则。**2026-10-28 被父任务 `prd.md` §12 取代**：轻量不是任务类型，而是尚未加载扩展包的最小闭环；二分类判定器与「自动升级为正式任务」规则取消。旧文内容保留在文末「历史：被取代的轻量任务规则」。

### 最小闭环内核

fstar 的底座是**永远可用的最小闭环**：默认不落盘、任何目录可用。

```
澄清目标 → 执行 → 基础检查 ↔ 修复 → 用户确认
```

三条不可裁剪的底线：① 实施与检查分离；② 检查失败必回修复循环；③ 最终完成只能由用户确认。

会话内过程节点 `clarifying / executing / checking / fixing / awaiting_user` **只用于路由**（决定主 Agent 下一步做什么），**不落盘、不承诺恢复**。会话结束即消失；不存在全局「轻量记录」。

### 扩展信号触发协商（取代旧判定原则）

不再有「默认轻量、满足 N 条自动升级」的判定器。主 Agent 按一条短路由规则（SessionStart 注入）处理：**按最小闭环接住请求 → 发现具体扩展信号 → 说明收益/代价 → 一次只推荐一个最高价值的包 → 用户同意后显式调用对应 skill**。

原 4 条判定原则转化为**扩展信号**（举例，非穷举）：

| 旧规则（自动升级） | 现含义（触发对应包的协商） |
|---|---|
| 预计跨会话 / 要中断后再继续 | → 建议持久任务包 |
| 涉及多文件、跨层、改公共接口 | → 视场景建议规划评审包 / 多 Agent 包 |
| 有可独立验收的交付物 / 用户要求产出文档 | → 建议规划评审包 |
| 需要拆分子任务 | → 建议持久任务包 + 多 Agent 包（仍一次只推荐一个） |

六个包、加载规则（默认整包、可裁剪、各包授权独立、拒绝后无新事实不重复问）见父任务 `prd.md` §12 与 `design.md` §2.4。

### 最小闭环 vs 持久任务包（取代旧「轻量 vs 正式」对比表）

| 项 | 最小闭环（默认） | 持久任务包（用户同意后） |
|---|---|---|
| 落盘 | **不落任何盘** | `task.json` + `events[]` + 归档 |
| 状态 | 会话内节点（仅路由） | 7 态状态机（本包的状态机） |
| `doc/` 产物 | 无 | 视是否启用规划评审包/测试评审包 |
| 检查 | 会话内基础检查 | 凭证链（指纹 + stale + 逐用例映射） |
| 用户验收 | **保留一次明确确认**（底线③） | `acceptance-<n>.json`（可核验来源） |
| 恢复 | 不承诺 | 跨会话恢复（租约 + events） |

关键差异：最小闭环**不做凭证链**（无版本指纹、无 stale 判定），因为不跨会话、不产生需复用的证据。**但用户确认不能省**——三条底线对所有形态生效。

### 中途加载不重做（取代旧「升级时的迁移」）

会话中途加载任何扩展包（含持久任务包）时：**不重做已完成的工作**。已会话内完成的澄清结论可直接写入新建的 `doc/prd.md`，已完成的检查可补记进 `acceptance/`，用户已给出的确认可写入验收记录——与旧「轻量转正式迁移」的目标一致，但触发者从「自动判定」改为「用户同意加载扩展包」。

### 历史：被取代的轻量任务规则（2026-10-28 被 §12 取代）

> 以下为 2026-10-26 确认的旧方案，保留作决策轨迹。**「自动判定 + 4 条升级规则」已取消**；「轻量保留验收确认」保留为最小闭环底线③；「升级迁移不重做」保留为「中途加载不重做」。

- 自动判定 + 可覆盖；轻量任务保留验收闭环，但不建任务目录。
- 4 条自动升级规则：跨会话；多文件/跨层/公共接口；独立交付物；需拆子任务。
- 轻量 vs 正式对比表（任务目录 / prd / 检查 / 验收 / 记录位置 / 归档）——已由上表取代。
- 轻量转正式时创建任务目录、补记结论与检查，不重做已完成工作。

## 四、技能数量与加载策略

- **13 个 skill 分两层**：核心 4 个自动触发（`fstar-execute` / `fstar-check` / `fstar-debug` / `fstar-help`）+ 协商路由 9 个（其余全部；含可选 UI）——总数上限 13 不变。
- 4 个 Agent 角色（research / implement / check / **editor**）。
- 核心 4 个靠 `description` 精确描述用户意图自动触发；协商 9 个由主 Agent 在扩展包获同意后显式路由（`skillOverrides` 降 listing 占用），不靠 description 匹配，也不靠主 Agent 记忆。
- 每次只加载命中的 `SKILL.md`；`references/` 按当前子任务再读。
- 不新增技能索引层（理由见前置修正 2）；不新增第 14 个 skill 承载扩展协商（协商是主 Agent 的路由规则，SessionStart 注入）。
