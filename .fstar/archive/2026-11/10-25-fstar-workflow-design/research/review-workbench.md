## 决定一：取消交付评审工作台，改为「评审稿」单一内容源（2026-10-27 用户确认）

**用户提问**：这个交付评审工作台有没有必要做？不做这种交付评审平台，实际在正常流程中也可以使用。

**结论：第一版不做工作台。** 理由：

1. 界面里的「确认/退回/已通过」会与 `task.json` 的 `awaiting_acceptance`、证据指纹、stale 判定形成第二套状态机，核心机制要同步两处。
2. 预览/交互/观察/分享四项都能在别处以更低代价满足。
3. 旧 Storybook 门户证明「好读性」不需要服务端——它作为**可选投影器**保留，不进 fstar 核心，第一版不做。

### 评审稿：人机共用的唯一内容源

取消「AI 版 prd/design + 人版评审稿」双轨。用户自己的旧扩展 `test-cases.zh-CN.md:3` 已经确定「不另写 AI 版」，fstar 沿用该结论。

```
<项目>/.fstar/tasks/<task>/
  task.json                  # 机器权威：状态、evidence[]（含评审证据）、指纹、关联
  doc/
    prd.md                  # 需求
    design.md                  # 技术方案
    test-cases.md           # 测试用例
    review-log.md           # 变更留痕（需求/方案变更与用例审阅事件投影）
  implement.md               # 仅 AI：执行计划
  research/                  # 仅 AI
  acceptance/                # 仅 AI：逐次运行报告（run id）
```

- 「测试用例」是评审稿，「测试执行报告」不是（沿用 `test-cases.zh-CN.md:56` 的分离）。
- 任务契约（范围、验收标准）写进评审稿正文，不另存一份 AI 版。
- 2026-10-27 曾拟把评审结论放入顶层 `task.json.review[]`；**2026-10-28 已简化**：不设该字段。用例批准只存 `evidence[]` 的 `kind: review`；prd/design 由启动确认定案。`doc/review-log.md` 改为三类变更事件的投影。

### 工作台四项职责的去向

| 原职责 | 去向 | 代价 |
|---|---|---|
| 预览 | 对话内渲染 + 可选 Storybook 投影器 + 任意 Markdown 阅读器 | Mermaid 终端不渲染 |
| 交互（确认/退回/批注） | 对话里下指令，Agent 改稿；用例批准写 `evidence[]` 的 `kind: review` | 不能脱离对话做 |
| 分享给同事 | `doc/` 文件夹直接发 | 同事批注不自动回流，靠用户转述并标 `source=user-relayed` |
| 观察开发状态 | `fstar status` / `fstar acceptance status` 输出表 | 不是常驻面板 |

### 数据格式影响（2026-10-28 简化，保留轨迹）

2026-10-27 曾拟给 `task.json` 加顶层 `review[]`（22 → 23 字段），结构如下；**该方案现已撤回**：

```json
{"artifact":"requirements","version":"v1","verdict":"approved|changes_requested",
 "by":"user","at":"...","notes":"...","source":"user|user-relayed|colleague"}
```

当前 `task.json` 为 **23 字段**（评审简化时为 22；2026-10-28 因新增扩展包授权 `extensions[]` 增至 23——与 2026-10-27 曾拟 `review[]` 时的「23」不是一回事，那个已撤回）。评审记录物理上只存 `evidence[]`（`kind: review`，并带上述 `verdict` / `by` / `at` / `notes` / `source`、`validates` 指纹与稳定条目 ID）；prd/design 的批准由 `planned → implementing` 启动确认及当时指纹记录，不要求单独命令。

## 决定二：结构约束 = 少量语义槽位 + 稳定条目 ID（2026-10-27 用户确认）

评审稿要同时给人读、给 Agent 精确定位条目，fstar 的约束强度定为**中间档**：

| 项 | 决定 |
|---|---|
| 强制 | 每个可被引用/验收的条目有**唯一稳定 ID**；少数字段（产物类型、版本、评审结论锚点） |
| 不强制 | 章节、布局、语言、图示形式；**ID 的写法**（默认模板给 `R-001`/`M-001`/`AC-001` 风格，换模板时做一次映射，之后按映射处理） |
| 禁止 | 让 fstar 靠自然语言语义猜条目指针（否则退回「意图识别错误」） |
| 变更 | 需求变更时按 ID 精确标过期，不整篇作废 |

## 决定三：模板由用户拥有、可替换（2026-10-27 用户确认，细节随决定二）

- 用户可替换章节、布局、语言、展示方式，可自带模板包。
- 旧扩展三份 zh-CN 模板作为**默认模板**进入安装包，不强制项目使用。
- 解析优先级：任务显式指定 > 项目模板 > 用户模板 > 安装包默认；任务记录模板来源与版本。
- 升级模板不追溯改写已评审的文档。
- 区分两类操作：**改模板**影响今后生成；**改本次产物**只影响本次文档。
- 首次映射可由 Agent 辅助并经用户确认，之后按保存的映射处理——与工具分类器「AI 不进分类路径」是不同机制，不冲突。

## 决定四：规范按主题归口（2026-10-27 用户确认）

**诊断先于方案**：固定目录本身不产生约束。Trellis 的 `spec/frontend/`、`spec/backend/` 之所以失效，不是分类分得不好，而是**新增规范时没有任何动作被强制执行**——Agent 写完直接落文件。目录形状既不检查、不提示、也不记录理由。所以有效的约束点在**新增前的那一步**，不在目录形状。

| | 做法 | 代价 |
|---|---|---|
| **A 主题归口（已选）** | 不预设 frontend/backend 骨架。每个规范主题记录「标识 / 适用范围 / 权威路径或章节 / 何时读取」；沉淀时先归入已有主题的章节，确实无归属才提议新增主题并说明理由 | 前期要做一次主题梳理；主题边界模糊时需人工裁决 |
| B 固定分类 + 强制归并 | 保留固定分类，新增必须落进既有分类的既有文件 | 「既有文件」膨胀成大杂烩；分类本身是猜的 |
| C 扁平 + 标签 | 不分目录，全靠 frontmatter 标签检索，index.md 可生成 | 丢掉「目录表达归属」，上下文裁剪只能靠索引条目承担 |

**决定内容**：

- 前端/后端降为**可选初始配置**，不是所有项目强制使用的骨架。
- 每个规范主题记录：主题标识、适用范围、权威路径或章节、何时读取。可指向已有文档，不要求复制。
- 沉淀流程：候选事实 → 判断是规范/知识/任务内决定 → 找已有主题 → 更新或补充已有章节 → 确实无归属才提议新增主题并说明理由。沿用先列候选、用户确认内容与归属后保存。
- 同一主题变大时可由单文件拆成目录，保留主题标识与索引入口。
- **不靠文件数量上限维持结构**——上限只会逼出「塞进最后一个文件」这种更糟的结局。
- 检查项：重复规则、冲突规则、无索引文档、失效链接、新增文件的归口理由。自然语言重复识别是 Agent 辅助，不声称脚本能完整判断。

## 决定五：评审闸门与证据（2026-10-27 确认，2026-10-28 简化）

「用户是评审者」要成为制度而不是姿态，但**不新增状态，也不设顶层 `review[]`**。评审结论只在确有需要时进入现有 `evidence[]`；prd/design 的最终批准由启动确认本身承载。

| 阶段 | 前提 |
|---|---|
| `drafting → planned` | 需求评审稿经用户口头/书面确认，`evidence[]` 记 `kind: review` 并绑定需求指纹 |
| `planned → implementing` | 用户启动确认 = prd/design 最终批准；状态转移 + 当时指纹即权威记录 |
| check 编写/补充测试前 | 用例已获用户 `approved` + 指纹新鲜；这是唯一必须单独落评审证据的批准 |
| `checking → awaiting_acceptance` | 再次校验用例批准 + 实际运行通过 + 指纹新鲜 |

- 用例评审证据与检查证据同样带 `validates` 指纹，可因源变更而 `stale`。
- 需求或用例一改 → 相关证据 `stale` → 有效状态落回并提示重审。
- **最小闭环豁免（2026-10-28 更新，原「轻量任务豁免」）**：未启用规划评审包/测试评审包时无此闸门——没有 `doc/` 目录、没有用例批准链，检查退回会话内基础检查 + 用户确认（三条底线仍生效）。
- 被否两案：评审只记录不设门槛；独立硬闸门。2026-10-28 进一步否决重复的顶层 `review[]`，避免同一结论双写。

## 决定七：文档维护三件套（2026-10-27 用户确认）

### 用户原话要点

1. 「需要保持 agent 读的 prd 和评审稿中的 prd 信息要一致」
2. 「在讨论过程中如果发生文件要修改的事，安排子agent专项去改文件内容」
3. 「这些事项看看是否还需要增加一个 skill 和 hooks 专门去做这些事」

**结论：三件套全部落地**——hook `doc-change` + skill `fstar-doc` + 角色卡 `fstar-editor`，职责分工见下节。

### 「保持一致」的解读

**取消双轨后，「一致」不是两份文件对齐，而是同一份文件的当前版本对所有读取方都新鲜。** agent 读的就是 `doc/prd.md` 本身，不存在第二份。真正的风险是「读到旧版」：

| 风险 | 现有机制 | 缺口 | 补法 |
|---|---|---|---|
| 主 agent 上下文里留着旧版 prd，后续推理基于旧内容 | 证据指纹 stale | stale 只影响**闸门**，不改 agent 脑子里的内容 | 由 `fstar-doc` 在改动后回读并提示重读 |
| 子 agent 被派发时拿到旧版 | `worker-context` 注入文件 | 注入时**没带版本/指纹**，worker 无法判断自己读的是哪一版 | `worker-context` 注入**必带版本/指纹** |
| 文件被改了，在途 worker 继续按旧的干 | `runtime-dispatch` 的变更传导只覆盖「对话里说的变更」 | **文件变更不触发传导**——真缺口 | 传导触发源扩到两种：① 对话里的需求变更；② `doc/*.md` 被改动 |
| 讨论中改动散落多处，无人统一校验 | 无 | 缺「改完回读校验」 | `fstar-doc` 的**回读校验**（语义槽位齐否、条目 ID 是否稳定、关联是否断、图文是否一致） |

### 三个组件各管什么（已确认采用三件套）

用户确认：**按「hook + skill + 角色卡」三件套落地**。

| 组件 | 数量 | 职责 | 为什么不能省 |
|---|---|---|---|
| **Hook `doc-change`**（PostToolUse） | 4 → 5 | 监听 `doc/*.md` 的 Edit/Write：重算指纹、**在非 `drafting` 阶段**标相关证据 stale（用例变更导致已有 review/check evidence 失效不受阶段豁免）、记 `events[]`、提示需变更传导 | 保证「**不漏**」——绕过 skill 的直接编辑也会被记账 |
| **Skill `fstar-doc`** | 12 → 13 | 「把讨论/评审里产生的修改落到文档，并保证改完仍一致」的统一入口：定改哪些 → 派专职子 agent → **回读校验**（语义槽位齐否、条目 ID 是否稳定、关联是否断、图文是否一致）→ 更新指纹/安排传导 → 回报改了哪几处 | 给「定点修改」一个能匹配上的 description——`fstar-clarify` 的触发是「需求不清/新功能/范围变更」，用户说「把 R-003 的异常分支改成先落库再发消息」匹配不上它，会漏触发 |
| **Agent 角色卡 `fstar-editor`** | 3 → 4 | 专职改文档：只允许编辑被指定的 `doc/*.md` 的指定条目；不新增/删除条目 ID（除非明确指示）；不自行决定评审结论；改完只回报 diff 摘要 | `implement` 角色带写代码权限与「完成实现」语义，会越界；专职角色的**上下文卫生**收益也最大——主 agent 只拿「改了什么」的摘要，不吃进整篇文档 |

**三者分工不重叠**：hook 负责「不漏」（被动记账，幂等、零噪声）；skill 负责「改得对」（判定改动量、定点修改、回读校验）；角色卡负责「谁改」（权限收窄到指定文件指定条目）。少任何一件都会留下缺口——没 hook 则绕过 skill 的直接编辑不被记账；没 skill 则定点修改无触发点；没角色卡则主 agent 吃进整篇文档且改写范围失控。

**skill 数量到 13 为上限**：宿主 listing 预算吃紧（见 `research/skills-detailed.md` 前置修正 2），且 fstar 的 skill 只有被调用过一次（`skillUsage` 分数 > 0）才能在贪心分配里赢过那批从未使用的 skill。13 条描述 ≤ 2,600 字符，落在单条 200 字符上限内。

### 与既有决定的边界

`research/hooks-skills-templates.md` 曾否掉「每次文件修改后自动检查」，理由是「频繁测试、反复写报告会干扰执行」。新 hook **不跑测试、不写报告、不输出噪声**，只做幂等的状态簿记——两者不是同一件事，文档里必须写明区别，否则后人会以为违反旧决定。

## 建议：同一事实源，多种阅读视图（随决定一/二生效）

- 需求、方案、用例各有权威内容与稳定条目标识。
- 用户视图包含流程图、业务解释、表格与评审批注。
- Agent 执行上下文按任务选取权威章节与条目，引用版本；摘要不能代替未读取的关键条件。
- 执行摘要是派生内容，不独立维护第二套要求。源更新后派生内容须重建或标为过期。
- 图示是正文的辅助视图；权限、金额、条件分支、异常恢复等规则必须有对应文字或表格。图文不一致列为待解决问题，不能静默挑选一份。
- Mermaid 是文本，AI 并非天然不能读；主要风险是图文重复、歧义、上下文过长及版本不一致。
- 暂不承诺任意图和自由文本之间的无损双向自动同步。

## 判断边界

用户日常可以以业务结果和证据为主要评审对象，不需要逐行读代码。但文档/预览正确不证明实现正确。自动检查、代码审查、真实环境测试和必要的专业人工审查仍属于交付流程。

逐用例至少区分：未运行、通过、失败、阻塞、跳过；展示关联交付版本、用例版本、执行环境、运行 ID 与证据。用例生成完成不能自动视为测试执行通过。

## 已确认：用例驱动检查（2026-10-28 定案）

1. 开发完成进入 `checking` 后，check Agent 根据**已写好的代码 + prd 条目**生成 `doc/test-cases.md` 草案；用户也可提供/修改。草案含**逐条目用例**（单点行为）与**场景链用例**（多个条目串成完整业务路径，落集成测试）。中途缺陷修复后针对修复点补用例。此前「规划/clarify 阶段生成用例」方案已作废。
2. 用户明确口头确认时，Agent 代记 `approved`（`source: conversation`，附用户原话引用与当时指纹）；证据写入 `evidence[]` 的 `kind: review`。供稿不自动等于批准。
3. **只有用例已获用户 `approved` 且指纹新鲜，check Agent 才能编写/补充测试代码并执行**。未批准、`changes_requested`、指纹过期或缺少用例时，停在用例准备/重审；不新增 phase。
4. check 按稳定用例 ID 写单元测试，场景链用例落集成测试。**禁止修改生产代码**；生产缺陷写 F-xxx 失败条目并转 `fixing`。
5. F-xxx 可附 unified diff 建议补丁，绑定问题 ID、用例 ID 与文件行号，**不自动应用**；fixing 轮 implement 可采纳、改写或说明理由否决。
6. 每轮输出 `acceptance/check-<n>.md`：逐条稳定用例 ID → 测试代码路径/标识 → 实际命令、结果与证据，带版本、指纹、run id、环境和状态。未运行、阻塞、跳过不得记作通过。
7. 用户改用例后，对应 review/check evidence 按稳定 ID 及依赖关系 `stale`；历史保留，重审重跑后才产生新鲜证据。

用例编辑导致失效不受 `drafting` 豁免；无已有证据的草案编辑无需生成 stale 记录。核心命令在读取/派发/回收/验收闸门重算校验，hook 是触发入口。
