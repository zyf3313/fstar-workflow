## 已确认：统一知识格式与 rule/memory 结构（2026-10-29）

- 不兼容 ECC：不读写 `~/.ecc/memory/`、不依赖 `ecc-universal`/MCP、不采用 `.cursor/rules` 或 `alwaysApply`。仅借鉴概念：未确认知识需人工提升、状态生命周期、不以 Agent 作为审批边界。依据 ECC `docs/design/ecc-memory-vault.md`（含 `schema/id/kind/scope/trust/status/links/supersedes` 与「no automated promotion transition」）；OpenSpec 无规则/记忆体系，无可借鉴结构。
- rule、memory、spec 使用同一 schema 家族 `fstar.knowledge.v1`，以 `type: rule|memory|spec` 区分；共用 `schema/type/status`，专属 `strength`（rule）、`kind`/`trust`（memory）；spec 无专属字段，正文仍按已确认的 Trellis 风格与英文。
- 字段取值改为自解释：`strength: enforced|default`、`status: active|superseded`、`kind: preference|lesson`、`trust: confirmed|unreviewed`。
- 只维护一份安装包内 `references/knowledge-format.md` 说明全部字段、取值、索引与模板，不为每种文件单开格式说明。
- 含义不靠 AI 猜测：加载器按 `type`/`status`/`trust` 过滤（unreviewed 记忆与 superseded 条目不进入上下文）；非法或缺失取值应明确报错而非静默取默认；强制性与项目规范的裁决由加载/裁决逻辑处理。
- rules/ 与 memory/ 文件内容用英文维护（与 specs/ 一致），讨论与解释用中文；任务文档仍默认中文。
- 正文保持短小断言式：rule 用 MUST/NEVER/APPLIES/NOT/SOURCE；memory 用内容 + APPLIES/NOT/SOURCE；不写背景叙述，不复制长代码。

## 已确认：debug / help / tools 内容定案（2026-10-29）

- `fstar-debug`：触发为同一问题反复失败、根因不明、检查多轮不通过。流程：停止盲目尝试 → 整理证据区分可靠与推测 → 候选假设按可能性排序 → 用判别性证据收敛 → 判定根因层级（实现/方案/需求）→ 返回对应环节（修复/设计讨论/clarify，沿既有回规划路径）→ 分析结论经 learn 沉淀。借鉴 Trellis break-loop 的根因分类表（规范缺失/跨层契约/变更传导失败/测试覆盖缺口/隐式假设）与贝叶斯推理框架（先验、证据更新、判别证据、置信度行动、防确认偏误与锚定）。debug 不大范围改代码、不直接写规范、不新增状态。
- `fstar-help`：识别问题类型（用法/配置/定制/故障排查），按当前配置与实际状态按需回答，指向对应入口与最小示例，只读不改状态。回答以实际安装版本为准。入口清单由安装包维护入口索引，help 依据索引与用户当前配置组装答案，不在 SKILL.md 硬编码入口。
- `fstar-tools`：查绑定 → 三层验证 → 调用与记录 → 缺口降级，触发点为干活需要该维度时及绑定失效；init 首次探测沿用本日确认。不自动安装、不自动改绑定、不替代验收判断。

至此 12 个 skill 的内容均已逐项核对（init/clarify/doc/plan/execute/check/continue/archive/learn/debug/help/tools）。

## 已确认：派发层原生优先 + 协议接口（2026-10-27）

**决策：v1 两个平台都用宿主原生子 Agent 派发，协议由 fstar 定义、适配器由 fstar 实现；对等进程运行时后置。**

### 关键澄清：协议归属 ≠ 传输方式

此前把「自研协作层」与「必须自建对等进程运行时」混为一谈。两者独立：

| 层 | 决定 |
|---|---|
| 协议（派发 / 转向 / 回收的语义） | 自研，参考 Trellis 协议思路（2026-10-26 已定，不变） |
| 传输（worker 跑在哪） | **宿主原生子 Agent**（本条新决定） |

原生子 Agent 是「自研协作层」的合格实现——协议由 fstar 定义、实现由 fstar 写，只借用宿主的进程模型。不用 Trellis channel 源码这一点不变。

### 理由

1. **四个差异化能力（验收闸门、证据失效、归档提醒、全局记忆）全都不在派发层。** 先建 1,670–2,310 行基础设施会推迟验证真正值钱的部分。
2. **原生在两平台都有机制**，不是只有 Claude Code 可用。
3. **代码量差 3–5 倍**（原生 ~600–1000 行 vs 运行时 1,670–2,310 行）；协议抽象对了，实现可替换。
4. **hook 注册点单一**：`worker-context` 天然就是 PreToolUse Task/Agent，不需要再造 channel 包装入口。

### 派发层只需满足的四项

1. 派发 implement / check / research / editor 四个角色
2. 中途把用户变更传给执行者
3. worker 完成/失败/取消 → 记录证据、安排检查
4. 跨会话「继续当前任务」时能接上

**租约 / 心跳属任务层**（状态机 ownership 维度），不是派发层职责。

### 必记风险

- **跨会话 worker 恢复在原生方案下未验证。** 会话级中断后能否 `claude --resume <sessionId>` 接上原生子 Agent，实测未做。
- 若不可用，v1 接受**重派**作为降级，并在 `fstar-continue` 契约里写明：`orphaned` 的首选动作从「唤醒原执行者」降级为「重派」。
- 状态机原文「唤醒原执行者并告知变化，重派是后备」的**首选 / 后备顺序在原生方案下可能需要反转**，取决于实测结果。

### 其他风险

- 原生子 Agent 的语义由宿主版本决定，平台升级可能改变行为；这部分不可控。
- Codex 侧原生派发的中途转向能力尚未实测。
- **派发本身会失败**（已在 Claude Code 实测遇到分类器超时），两条路径都必须有重试与明确失败状态。

### 参考：Trellis 的教训

Trellis 同时维护 `.claude/agents/trellis-*.md`（原生）与 `.trellis/agents/*.md`（channel worker），其文档自承「两个派发路径不能混成一套自动互通的文件」。**混合方案的长期代价是两套语义并存**——这是不选混合的原因。

### 后置条件

对等进程运行时不是永久放弃，是**后置**。触发重新评估的条件：

- 跨会话 worker 恢复在原生方案下确实不可用，且重派降级影响实际使用
- 需要运行时不支持的平台
- 原生语义变动导致不可控

届时协议已定，实现可替换——这也是先定协议的价值。

## 已确认：规范按主题归口（2026-10-27）

**诊断先于方案**：固定目录本身不产生约束。Trellis 的 `spec/frontend/`、`spec/backend/` 失效不是因为分类分得不好，而是**新增规范时没有任何动作被强制执行**——Agent 写完直接落文件。目录形状既不检查、不提示、也不记录理由。有效的约束点在**新增前的那一步**，不在目录形状。

| 项 | 决定 |
|---|---|
| 骨架 | 前端/后端降为**可选初始配置**，不是所有项目强制使用的骨架 |
| 主题 | 每个规范主题记录「标识 / 适用范围 / 权威路径或章节 / 何时读取」；可指向已有文档，不要求复制 |

| 拆分 | 同一主题变大时可由单文件拆成目录，保留主题标识与索引入口 |
| **不做** | **不靠文件数量上限维持结构**——上限只会逼出「塞进最后一个文件」这种更糟的结局 |
| 检查 | 重复规则、冲突规则、无索引文档、失效链接、新增文件的归口理由。自然语言重复识别是 Agent 辅助，不声称脚本能完整判断 |

被否的两案：固定分类 + 强制归并（「既有文件」膨胀成大杂烩，分类本身是猜的）；扁平 + 标签（丢掉「目录表达归属」，上下文裁剪只能靠索引条目承担）。

## 已确认：文档维护三件套 hook + skill + 角色卡（2026-10-27）

用户提出三点要求：① 保持 agent 读的 prd 与评审稿中的 prd 信息一致；② 讨论中要改文件时，派专职子 agent 改；③ 这几件事是否还需要专门加一个 skill 和 hooks。

**结论：三件套全部落地。**

### 「保持一致」的定义

取消双轨后不存在第二份 prd，所以「一致」**不是两份文件对齐，而是同一份文件的当前版本对所有读取方都新鲜**。要补的是四个「读到旧版」的缺口：

| 缺口 | 补法 |
|---|---|
| 主 agent 上下文里留着旧版 prd，后续推理基于旧内容 | 指纹 stale 只影响闸门、不改 agent 脑子里的内容 → `fstar-doc` 改完回读并提示重读 |
| 子 agent 被派发时拿到旧版 | `worker-context` 注入**必带版本/指纹** |
| 文件被改了，在途 worker 继续按旧的干 | 变更传导触发源扩到两种：① 对话里的需求变更；② `doc/*.md` 被改动 |
| 讨论中改动散落多处，无人统一校验 | `fstar-doc` 的**回读校验**（语义槽位齐否、条目 ID 是否稳定、关联是否断、图文是否一致） |

### 三个组件

| 组件 | 数量 | 职责 |
|---|---|---|
| **Hook `doc-change`**（PostToolUse） | 4 → 5 | 监听 `doc/*.md` 的 Edit/Write：重算指纹、**在非 `drafting` 阶段**标相关证据 stale（用例变更导致已有 review/check evidence 失效不受阶段豁免）、记 `events[]`、提示需变更传导。**不跑测试、不写报告、不出噪声** |
| **Skill `fstar-doc`** | 12 → 13 | 定点修改的统一入口：判定改动量 → 小改自己做 / 跨文件或大段重写派 `editor` → **回读校验** → 更新指纹与 stale → 安排变更传导 → 回报改了哪几处 |
| **角色卡 `fstar-editor`** | 3 → 4 | 专职改文档：只改被指定的 `doc/*.md` 的指定条目；不增删条目 ID（除非明确指示）；不自行决定评审结论；不改代码；只回报 diff 摘要 |

**分工不重叠**：hook 管「不漏」（被动记账、幂等）；skill 管「改得对」（定点修改 + 回读校验）；角色卡管「谁改」（权限收窄 + 上下文卫生）。

**与旧决定的边界**：`research/hooks-skills-templates.md` 曾否掉「每次文件修改后自动检查」，理由是会干扰执行。新 hook 只做幂等状态簿记，两者不是同一件事，文档里已写明区别。

**skill 数量到 13 为上限**：宿主 skill listing 预算吃紧，且 fstar 的 skill 只有被调用过一次才能在贪心分配里赢过从未使用的 skill。

## 已核实：Claude Code 的 skill listing 预算机制（2026-10-27）

在安装的二进制 `~/.nvm/.../@anthropic-ai/claude-code/bin/claude.exe`（**2.1.311**，即本机运行版本）中核实，含内嵌 schema 原文与本机实测。

### 修正了此前的三处错误表述

| 此前说法 | 实际 |
|---|---|
| 预算约 2,720 **tokens** | 单位是**字符**：`上下文 token × 每 token 字节数(回退 4) × skillListingBudgetFraction(默认 0.01)`。本机 `CLAUDE_CODE_MAX_CONTEXT_TOKENS=272000` → **10,880 字符** |
| 超预算的描述被**丢弃** | 描述**降级为 name-only**（`- skill-name`），skill 不被移除。**自动触发照样失效**——结论对，机制错 |
| 「339 个 skill 是问题，用户策展即可」 | 339 个 skill 的**名字就占 6,247 字符（预算 57%）**，描述共 90,930 字符。**光靠「描述写短」救不回来** |

### 关键机制

- **分配算法**：内置 skill 永远保留完整描述；其余按 `usageCount × max(0.5^(距上次使用天数/7), 0.1)` 贪心分配。**从未被调用过的 skill 分数为 0，平局全输**——fstar 的新 skill 会第一批被降级。
- **`skillOverrides`**：真实设置项，取值 `on` / `name-only` / `user-invocable-only` / `off`，**按 skill 名精确匹配，无通配符**。后两者**完全不进模型清单，消耗 0 字符**。`/skills` 写的是项目 `.claude/settings.local.json`；用户全局 override 需手工写 `~/.claude/settings.json`。
- **`disable-model-invocation`**：SKILL.md frontmatter 布尔字段，为 true 则模型不可调用且**消耗 0 字符**。
- **按项目过滤用户级 skill**：**不存在「包含」机制**，只有用 `skillOverrides` 做**排除**。
- 插件 skill 不受 `skillOverrides` 影响；fstar 装在 `~/.claude/skills/` 属普通 skill，受影响。
- 使用数据在 `~/.claude.json` 顶层 `skillUsage`。

### 对 fstar 的方案影响

原方案「描述压到 ≤700 tokens + doctor 告警」**不够**。改为 7 条措施，核心是**首次调用清单**（任一次调用写入 `skillUsage`，分数 > 0 后永久优先于从未使用的 skill）+ `fstar doctor` 按公式重算预算并明确告警。

完整机制、实测数据与 7 条措施见 `research/data-formats.md` §4.1。

## 已确认：分类器用 Python 写，不用 AI 分类（2026-10-27）

用户提出：分类器（把本机工具归到能力维度）**用 Python 实现，不交给 AI 判断**，理由是浪费用户 token、拖慢初始化速度。已采纳。

### 决策内容

| 项 | 决定 |
|---|---|
| 实现语言 | Python（与已定的「Node CLI + Python 脚本」打包形式一致，不是新增约束） |
| 硬约束 | **AI 永不进入分类路径** |
| 允许 AI 的两处 | ① 解释绑定提案的自然语言部分；② 判定「工具自述完全缺失的新 MCP server」这类真模糊情形。**两处都不在初始化热路径** |
| 未知工具 | **注册表 → 通用探针 → 手动**三档：已知工具走声明式注册表（精确）；未注册工具走维度级通用探针（召回）；都未命中的列为「未分类候选」，由用户手动绑一行 |
| 不引入 | 「AI 辅助分类」这一额外层 |

### 理由（除用户给出的 token/速度外）

1. **确定性**——同样输入必得同样结果。AI 分类每次可能不同，导致绑定漂移、diff 噪声、无法写回归测试。
2. **可版本化**——分类规则进 git，能 review、能回滚。基础设施的输出不该由非确定性组件产生。
3. **可脚本化验证**——三层验证（可发现 → 客户端加载 → 一次最小真实调用）大部分可写成确定性脚本；「最小真实调用」可用「从项目抽一个已知符号 → 跑工具 → 比对 `file:line`」实现，CodeGraph 能否索引本仓库由脚本判定，无需 AI。

### 代价与缓解

| 代价 | 缓解 |
|---|---|
| 新工具出现时，注册表要等 fstar 发版才认识 | 用户可先写 `~/.fstar/tools/registry.d/*.yaml` 自救；探针层可先抓到并提示 |
| 通用探针按模式匹配，可能误报 | 探针命中一律标 `weak`；升为 `strong` 必须经注册表或用户确认 |
| 工具自述质量差时仍会误判 | 无法根除。已列为遗留难点 6 |

### 性能边界

分类器**不进每轮 hook 热路径**：完整扫描只在 `fstar init` 或显式 `fstar tools scan`；`session-context` hook 只做 `shutil.which` 存在性检查 + `detected_at` 过期判断；`turn-context` 完全不碰工具。

## 已确认：状态机改三态（2026-10-28 定案）

> 取代此前「7 态状态机」。决策轨迹：曾定 `drafting → planned → implementing → checking → awaiting_acceptance → done → archived` 七态，2026-10-28 用户拍板向 Trellis 对齐，瘦身为三态，并把「检查分离」「验收闸门」两条底线从状态机改由命令校验 + 证据前置 + 派生标记承载。

**三态**：

```
planning → in_progress → completed
     ↑          │  ← 检查失败 / 用户否决「改改」回这里继续干
     └──────────┘
任意非终态 → dropped（遗弃戳，不是正常站点）
归档 = 命令不是状态（搬目录 + 记 archivedAt）
```

**为什么三态成立**：

- `checking` 并入 `in_progress`——实施与检查分离靠**角色 + 证据**执行（completed 的前置是「check 角色的新鲜通过证据」+「用户 `acceptance`」），不必占状态。
- `awaiting_acceptance` 不是实体态（无人在干活、无租约、无进行中工作），改由两点承载：
  1. **`completed` 只能由用户命令写入**（`fstar accept` 或 finish 流程里用户点头）；Agent 无法推完成。命令校验：check 通过证据新鲜 + `acceptance` 字段齐全（`confirmed_by: user` + 可核验来源 + 当时指纹）。
  2. **「待验收」派生标记**：`fstar state show` 计算「check 通过 ∧ 证据新鲜 ∧ 无租约」→ 显示 `⏸ 待验收`，不落盘、证据一过期自动消失。
- 验收否决按**用户原话路由**：说「改改」→ 回 `in_progress`；说「方向错了」→ 回 `planning`；没说清则问一句。

**三态相干的既有决定平移**：

| 原 7 态决定 | 三态下 |
|---|---|
| `awaiting_acceptance → done` 仅用户 | `in_progress → completed` 仅用户（`fstar accept`） |
| 证据 stale → 落回 `checking` | 落回 `in_progress`（fixing 并入） |
| `done → archived`（判据+用户确认） | 归档命令 `fstar archive`：判据满足 + 用户确认，搬目录记 `archivedAt` |
| `dropped` 任意态可落 | 不变：仅用户可 drop、处置必选（保留现场/丢弃现场/转知识）、可复活回 `planning` |
| 容器相位推导（空壳） | 不变：取子任务最靠前非终态；全 completed/dropped → 容器可验收 |
| 中途加载持久任务包迁移 | 一律从 `planning` 重走（已完成工作保留进 evidence，不重做） |
| `blocked` 按写入者解除 | 不变：Agent 不能自写自解，用户标的用户解 |

删除 `turn-context` 的理由：其「每轮刷新提醒」职责与「提醒挂靠归档后、不打断用户」冲突（Q3 已定）；「待验收标记」已由 `fstar state show` 从证据计算输出，无需每轮注入；phase 由主 Agent 自己命令改动，不会自过期。

**派发协议边界**：

- **失败重试**：最多自动重试 **1 次**（带上次失败原因），仍失败则停派发进 `fstar-debug` 根因归类，不无脑重试。
- **跨会话恢复**：worker 派发后会话被杀 → 租约 30 分钟过期成孤儿租约 → `fstar continue` 发现后**只读不重派**，向用户报告「上次干到一半断了」，用户决定接管/重派/放弃；接管写 `takeovers[]`（原 holder + 原因 + 新 owner），并核对该 worker 遗留产物是否抢救得回（明确告知缺失）。**只能恢复状态，不能假装 worker 还活着**。
