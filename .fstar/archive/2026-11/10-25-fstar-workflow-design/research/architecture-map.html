三条不可破的边界

边界 1
存储层 → 底座是单向强制。所有状态写入走 fstar task state set，命令内部校验转移合法性；Agent 不能直写 task.json。
边界 2
Hook 从不写状态。它只做定位、注入、提醒；所有判定永远在核心命令层。
边界 3
方法细节不写两遍。角色卡只写权限、输入契约、交付格式、禁止事项；方法细节在 skill 的 references/。

六个维度的职责边界

维度负责明确不负责
Hooks宿主事件发生时定位上下文、触发提醒、注入最小信息状态转移校验、耗时调研、代替用户验收
Agents规定执行者权限、输入契约、交付格式、禁止事项重复写方法细节（方法在 skill reference）
Skills告诉 Agent 一类工作怎么做保证状态转移合法、代替命令
Templates产物骨架执行命令、授权记录、自动触发
目录结构内容归属与持久化运行状态（分离在 runtime/）
核心命令校验批准、版本、证据、租约、状态转移语义判断（语义在 skill / agent）

状态机的三个维度

维度含义性质
phase 阶段走到哪一步标量、互斥、可推进
evidence 证据支撑当前阶段的产物可失效（指纹变化 → stale）
ownership 在途谁在做（会话租约）可丢失、可过期（心跳超时 → orphaned）

blocked 不是阶段，而是阶段上的属性 { reason, since }，解除后回到原阶段。dropped 是终态阶段。

回规划转移（2026-10-26 补）

planned / implementing / checking / fixing → drafting：Agent 发起，必须带回规划原因（需求/设计根本性变更，或 debug 判定根因在需求侧），全部证据标记 stale，租约释放。done 不重开 drafting——重开走 done → implementing。这条转移同时是 fstar-debug「必要时回规划」和中途需求大变更的合法路径。

系统必须硬拒的情况

  • Agent 写 done 或 archived
  • drafting → implementing
  • checking → done
  • stale 证据下进 awaiting_acceptance
  • 容器在子节点未全 done/dropped 时进 awaiting_acceptance

归档判据

phase = done  ∧  子节点 ∈ {done, dropped}  ∧  无 stale 证据  ∧  无未决问题

规范优先级（已确认）

场景生效内容
项目有明确规定用项目的，覆盖全局对应项
项目没规定用用户级 rules/ 补缺
两者都没说走产品默认行为

按事项与适用范围判断是否覆盖，不因为存在一个项目规范文件就忽略全部全局规则。不回写全局：某个项目的例外不会自动改变其他项目。 此优先级只管 fstar 的用户/项目内容，不改变宿主系统指令、权限限制或用户当前明确指令。
