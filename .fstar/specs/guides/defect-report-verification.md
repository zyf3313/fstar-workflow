# 外部缺陷报告核对规范

> 适用：收到一份缺陷报告、优化建议、AI review 或会话摘录，准备采纳、
> 排期或改动代码之前。
> 目标：把「报告说有问题」变成「本机/本版本确实有问题、证据是什么、
> 该怎么处置」。

---

## 核心规则

**先核对，后行动。** 报告的严重度、标题和语气都不是证据；每条结论必须
落到源码位置、运行输出或可复现数据上。核对阶段保持只读。

---

## 步骤

### 1. 固定基线

- 记录来源、采集时间、采集机器/用户、报告声称的版本。
- 确认本机实际版本：`fstar version`、`package.json`、`git log -1`。
- 基线不一致时，结论只按本机版本表述；跨机器数据不当作本机事实。

### 2. 拆成可判定条目

- 一条一个 claim，沿用报告编号，不要整章接受或整章否定。
- 每条标注类型：
  - `机制`：源码分支、命令入口、错误信息、hook 行为。
  - `数据`：某台机器上的任务、事件日志、doctor 输出。
  - `建议`：当前版本尚无对应实现。

### 3. 逐条取证

- 机制：给出 `file:line`，或实际命令 / hook 的输入输出。
- 数据：必须在本机复现；跨机器数据只能标「无法核实」。
- 建议：先查当前版本是否已有替代实现（命令、字段、错误信息）；
  已实现则标「已过时」，不要重复设计。

### 4. 给出结论分级

| 结论 | 条件 |
|---|---|
| 已确认 | 至少一条本机可复现证据 |
| 部分成立 | 分别写明成立与不成立的部分 |
| 不成立 | 有明确反驳证据（字段存在、退出码、代码分支） |
| 无法核实 | 缺数据 / 不同机器 / 需要特定状态；写明缺什么 |
| 已过时 | 当前版本已修复，或已有替代能力 |

### 5. 区分机制与数据

- 源码只能证明「允许 / 禁止 / 缺少入口」，不能证明「某个项目里发生了 N 次」。
- 任务数量、事件日志重复、`related_tasks` 为空、doctor 输出，都属于
  数据事实，必须单独取证。
- 报告采集自另一台机器时，数据类条目一律标「无法核实」，不靠推断补齐。

### 6. 处置，而不是直接开工

- 每条给：采纳 / 已有替代 / 不采纳（理由）/ 需要用户决策。
- 报告作者的 P0/P1 不自动等于本项目的优先级。
- 采纳的条目再进入 fstar 任务流程（create → plan → implement → check）。

### 7. 核对阶段保持只读

- 不改代码、不改任务状态、不写规则/规范、不运行会写数据的命令。
- 需要把核对结论沉淀为规范时，按 fstar 授权路径单独处理。

---

## 输出格式

```markdown
| # | 报告结论 | 核对结论 | 证据 | 处置 |
|---|---|---|---|---|
| B-01 | …… | 已确认/部分/不成立/无法核实/已过时 | file:line 或命令输出 | 采纳/已有替代/不采纳/待定 |

## 无法核实的条目
- B-xx：原因（不同机器 / 缺少数据 / 需要特定任务状态）
```

---

## 与其他规范的关系

- 与 `impact-check-guide.md` 互补：本规范管「报告是否真实」，
  impact-check 管「改完之后还影响了什么」。
- 与 `guides/index.md` 的 AI 交叉评审规则一致：每个 CRITICAL/WARNING
  都要落到代码；本规范把范围扩展到所有外部缺陷/优化报告。
- 核对结论是后续任务的事实输入；不要把报告原文直接当作任务验收标准。
