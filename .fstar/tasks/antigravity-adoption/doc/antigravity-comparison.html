01Antigravity 是什么

Google 于 2025-11-18 与 Gemini 3 同日发布的 agent-first 开发平台。核心四原则：Trust / Autonomy / Feedback / Self-improvement。产品形态包括 Agent Manager（桌面）、IDE、CLI、SDK 及各 IDE 扩展。多模型可选（Gemini 3 Pro / Claude Sonnet 4.5 / GPT-OSS）。

与 fstar 属同一类东西：计划门 → 实施 → 独立验证 → 知识沉淀的任务工作流系统。

03建议采纳的四个点建议采纳

① Artifact 交接制 核心

Antigravity Teamwork 中 agent 间不共享会话上下文，全部通过 workspace 内结构化 artifact（Request / Plan / Progress）协调，官方明确以此解决长项目上下文膨胀。落到 fstar：联调期任务通过文件继承父任务知识，而不是靠人重新解释。

② 每条需求绑定独立客观验证方式

Teamwork Phase 1 访谈强制每个需求块写清"怎么证明做到了"，Auditor 后续核对证据与真实命令输出、防 mock/跳过。fstar 的 plan_item 目前只写"做什么"——联调期问题一半源头在验收标准含糊。

③ Challenger 型检查

/boost 的 implement → challenge → fix → re-verify 管线：不只验证"做了"，还专门构造反例和边界用例。可作为 fstar-check 的规则增强，不动内核。

④ Walkthrough 标准化收尾产物

统一"改了什么 + 如何验证 + 证据（命令输出/截图）"的收尾文档格式。它同时是联调任务最好的背景材料——①的注入源。

04核心场景：大需求联调期的断链与修复

左边是现状，右边是借鉴 Artifact 交接制后的改造

现状（断链） ───────────────────────────────────────────────────────── 大需求 ──计划─→ 子任务... ──全部验收─→ ✅ archive/大需求/ ├─ prd.md ├─ design.md └─ (终点，知识锁死) 联调期：用户报问题 → 开孤立任务 A → 归档到 2026-11/ 平铺 → 开孤立任务 B → 归档 → 开孤立任务 C → 归档 ✗ A/B/C 互不知晓，context 里没有父任务设计，事后无法回溯完整边界
改造后（树会生长） ───────────────────────────────────────────────────────── 大需求 ──计划─→ 子任务... ──全部验收─→ ✅ archive/大需求/ ├─ prd.md ├─ design.md ├─ walkthrough.md ★④ 统一收尾产物 └─ followups.md ★聚合联调任务 联调期：用户报问题 ↓ prompt-state 识别问题落在已归档大需求范围内 ↓ 修复任务 A：origin: 大需求ID ★① 来源标记 ↓ dispatch 时自动注入 ← design.md ← walkthrough.md ★③ 上下文继承 ↓ fstar-check（+ Challenger 构造反例 ★②） ↓ ✅ 归档 → 自动写进父任务 followups.md ★归档聚合 ✓ 树"生长"而非断裂；联调任务继承需求上下文；一条链路看全完整度

07明确不做的不做

机制原因
异步 inline 评论不打断执行依赖 host UI 形态，成本高、收益存疑
/swarm、/boost 等命令形态与 fstar "少命令、规则内嵌" 方向相反
浏览器录屏 artifact依赖 IDE 形态，CLI 场景不适用
Integrity modes 三档role card / capabilities 已有等价物
