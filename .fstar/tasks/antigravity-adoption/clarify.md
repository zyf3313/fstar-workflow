# Antigravity 借鉴落地与联调任务关联修复

调研 Gemini Antigravity（agent-first 开发平台，2025-11-18 发布）后的落地任务。核心借鉴点是 Artifact 交接制：任务间通过文件交接上下文而非依赖人工重新解释。

## 用户确认的方案方向（本会话）

1. 联调/修复任务作为大需求任务的**子任务**存放（parent 关系），不再开孤立平铺任务。
2. 即使大任务已归档，也将其**挪出（reopen）**回任务文件夹挂子任务；完成后**父子一起重新归档**。reopen 是显式状态转换并留事件痕，不是静默文件移动。
3. 配套：origin 链字段、dispatch/check 上下文继承、plan_item 绑定验证方式、fstar-check Challenger 规则、walkthrough.md 标准化。
4. 讨论材料 antigravity-comparison.html 移入项目正式位置。

## 流程反馈（2026-11-28 第二轮）

用户指出澄清流程缺陷：任务创建后应继续需求探讨直到澄清为止，而非直接推进到规划/下一阶段。确认的修正表述：任务创建是早期动作，创建后 coordinator 回到需求探讨循环；澄清未完成前不生成规划文档、不推进阶段。同条消息中的"可以开任务"不得跳过对意见征求的回应。

## 派发模式反馈（2026-11-28 第三轮）

用户确认优化方向——对话中创建任务、改写文档全部交由子 agent 完成，主 agent 主要职责是与用户对话和派发活；用户明确说明这是对工作流的优化项，不是知识沉淀。原话："我在对话的时候向创建任务还有改写文档能不能全交由子agent的去做 主agent的主要职责就是跟用户对话然后派发活 这个是我想对工作流的优化项不是学习沉淀规则"。

## 澄清与协同反馈（2026-11-28 第四轮）

用户原话："还有需求探讨这个 我觉得现在缺少 类似 grill-me 这种刨根问底试的skill，现在有点我主动提问题的意思，我已希望需求探讨的skill 能补足点这类问题 还有一点就是要自身多利用工作流本身的agent替你做事协同调度"。确认的处理：clarify 内嵌对抗追问模式而非新增 skill（少命令原则），协同调度作为 A-008 执行面入 routing（见 A-011）。

## 设计决策与澄清重整（2026-11-28 第五轮）

(a) 用户对三个悬置问题的决策：
- 多 host 一致性——支持子 agent 能力的 host 走纯派发，不支持的降级为主 agent 直接执行。
- antigravity-comparison.html 最终位置——当前任务 doc/ 文件夹（.fstar/tasks/antigravity-adoption/doc/）。
- 发布节奏——不着急发布，统一改完验收完一次发布（不拆批）。

(b) 澄清 skill 重整反馈原话："还有就是探索这一点 不主动提问题，每次都要我去问整体出的任务有啥问题没然后再去做，你好好吧需求探索这部分skill整理下"。确认的重整方向：fstar-clarify 重构为探索主导式（A-012 四条规则：每轮主动出题、主动 grill、立场前置、收口自查）。

## 规划时序反馈（2026-11-28 第六轮）

用户原话："plan.md 我记得 是在整个 实时任务前 需求单套结束后 设计稿也出完了然后接着是 plan 然后再继续按照plan.md 去派发执行，相当于是个总任务仓类似那这个plan.md明显是有问题的 你具体查出问题原因和机制 需要对此修复下"。

确认的正确时序：clarify 收敛 → design → plan → 派发执行。查出的三层机制缺陷：plan 触发为语义判断无约束、design 与 plan 无顺序约束、start 无门禁（对应 A-013）。

## 调研背景摘要

Antigravity Teamwork 模式中 agent 间通过 workspace 内结构化 artifact（Request/Plan/Progress）协调，不共享会话上下文，官方明确以此解决长项目上下文膨胀；其 Phase 1 访谈强制每条需求绑定独立客观验证方式，Auditor 核对证据防 mock；`/boost` 管线（implement→challenge→fix→re-verify）提供对抗检查思路。已同构部分不重做：计划门、显式 gate、独立检查（fstar-check）、知识沉淀（fstar-learn）、上下文收据（v0.12）。

## 待确认事项

无阻塞性待确认项；细节（origin 字段最终命名、注入文档清单）可在设计阶段定。
