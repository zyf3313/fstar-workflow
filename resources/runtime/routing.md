# fstar routing

This is the sole package routing source. It decides what to invoke before invocation; commands remain responsible for state validation.

## Always-available minimal loop

Clarify the goal in conversation, invoke `fstar-execute` through the host native implement role, invoke independent `fstar-check`, return every failed check to repair and recheck, then wait for explicit user confirmation. Session nodes are not persisted and no fstar metadata is created. This does not prohibit delivery files. Never fall back to main-Agent production editing. `fstar-debug` is core-automatic: route to it when a native dispatch fails twice (at most one automatic retry, with the prior reason) or a repair shows no progress.

## Extension negotiation

Package IDs are exactly `planning-review`, `persistent-task`, `multi-agent`, and `project-governance`. Grants are independent. Reuse an existing grant. Otherwise explain benefit and cost and recommend only one highest-value package. Default to full scope, allow explicit custom included/excluded capabilities, but never remove implement/check separation, repair after failure, or user-only completion. After refusal, continue the minimal loop and do not ask again unless new facts materially change value or cost. Planning authorization does not create task.json. Mid-work authorization imports valid work without redoing it. A user-supplied planning document (PRD/design/clarify content) must be stored into the current task directory before any implement dispatch: `doc/prd.md`/`doc/design.md` adapted to the template structure with origin noted, which requires the planning-review grant with the corresponding `prd`/`design` member, so negotiate that grant first when absent — a user handing over planning material is a new fact that materially changes value; clarify content stays under the `clarify` member. Never dispatch implement while user-supplied planning material is still unstored; for session-only work without a task directory, the material stays in the conversation record passed to dispatch.

The session context always lists the four optional packages and injects the project and user indexes read-only. Discovery and reading never imply authorization. When the user states a durable convention or asks to record something, treat it as a session-node learn candidate: if no grant covers the destination (`rules` or `memory` under `project-governance`), offer that package before writing anywhere. Never silently fall back to a host-level memory; if the user declines the fstar path, say so explicitly.

Before consuming a package member, check that member is in the current grant's `included` list; `excluded` and unlisted members are unavailable. Task recovery reads the task's `extensions` records; never substitute `capabilities`, which is a separate schema field and never authorizes workflow behavior. For session-only work, retain the authorization records returned by `extension enable` in the caller's session and pass them as the `extensions` array in hook and dispatch JSON payloads. On disable remove that record from subsequent payloads. Separate CLI invocations cannot remember these grants. These records guide cooperating callers and are not a same-permission security boundary.

- Planning/review need: use `fstar-clarify` only with `clarify`, `fstar-doc` only for included `prd` or `design`, and `fstar-plan` only with `plan`. Use the editor and document check only when their respective members are included. `fstar-clarify` hands off to doc or plan only when its design-tree frontier is empty: an unanswered frontier question is an unresolved requirement, not optional context.
- Persistence/recovery need: `fstar-continue` requires `recovery` (pass `--workflow`), `fstar-archive` requires `archive` (pass `--workflow`), and `fstar dispatch orphan <task> --workflow` requires `recovery`. These workflow consumption entries reread the stored grant at call time.
- Safety machinery always on: the `task`, `evidence`, `lease`, and `events` members never gate task consistency or recoverability. Evidence staleness and invalidation, lease acquisition/renewal/expiry/takeover, whole-tree archive recovery, and append-only event integrity keep running for any persistent task regardless of how those members are trimmed; harvesting a worker result, invalidating evidence, or recovering an interrupted archive never checks an extension member. Custom trimming of `task`/`evidence`/`lease`/`events` only records the user's intent to skip optional persistent-lifecycle workflow consumption; it can never disable safety bookkeeping.
- Enhanced collaboration: require `research`, `parallel-implement`, `version-injection`, or `change-propagation` for the respective enhancement; base implement/check remains available.
- Governance: use specs, knowledge, rules, or memory only with the corresponding included member; route learning according to its actual destination. Project initialization and its user-root creation are exempt from the learn-approval requirement: `fstar init` may create the skeleton and auto-create or repair the user root before any governance grant exists, but later writes to specs, knowledge, rules, or memory still require the included member, the learn proposal, its hash, and the user's exact confirming quote.

A recall intent queries indexed knowledge and archived task listing with sources and applicability differences; it does not restore an archived task and has no recall skill. Continue resumes only the current task and never scans archive candidates. Only after a successful `fstar-archive` operation may routing show other long-unarchived candidates; reminders never auto-archive. `fstar-help` explains observed installed entries only.

Two learning-loop rules apply before proposing anything. First, rejected proposals: before proposing an approach, check the project's rejected ledger (`.fstar/knowledge/references/rejected.md`, one index line injected at session start; read the file when the line is present) and the user's rules for previously denied approaches — a hit means do not re-propose it; cite the user's recorded words when asked why. Recording a rejection follows the normal `fstar-learn` authorization pipeline (project-governance `knowledge` member, proposal, hash, and the user's exact quote); it is never recorded silently. Second, corrections: when the user explicitly rejects or corrects produced output mid-task, the coordinator records one `fstar correction record` event carrying the user's exact words as `user_signal` (pure capture, no knowledge write, no behavior change, no grant required) and then continues the task; do not interrupt the flow to offer a learn candidate until the work settles.

Acceptance stays user-only, with one authorized exemption path: a user-recorded rule may delegate acceptance for a class of work (for example "docs-only changes with a green final check"). When the final check is fresh and an active rule in the user's rules or project specs explicitly covers the task's class of work, the coordinator may record acceptance citing that rule's source and quote in the event data (`accepted_via_rule`), and must surface the citation to the user at the next turn. No rule match, no exemption — priority or risk level alone never waives acceptance; and every exemption traces to the user's recorded words.
